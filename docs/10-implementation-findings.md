# 10 · 实现发现（文档 vs 代码的对比账）

> 目的：设计文档 → 参考实现的过程中，暴露出的**文档没说清、说错了、或实现才知道的问题**。
> 这一页的价值在于：它记录了「文档成立」与「系统可用」之间的差距，而不是粉饰 demo。
>
> 版本：v0.1 ｜ 日期：2026-10-31 ｜ 全部条目均有实测数据支撑

---

## 0. 一句话结论

**demo 已可跑通并演示，但离"可上线"还差三件事**：① 分数上限不可达（F-01）；② 三分之一规则在现有解析能力下无判别力（F-02）；③ 评测集是合成的，不能证明审美判断质量（F-06）。

## F-01 · 「强烈推荐」档在现有规则集下**不可达**（严重）

### 实测

跨 10 个剧本 × 5 个场合（50 组）扫描：

| 指标 | 实测值 | 文档预期 |
|---|---|---|
| 分数范围 | **45.4 – 79.0** | 0 – 100 |
| 跨度 | 33.6 | — |
| 强烈推荐（≥80）占比 | **0.0%** | 应可达，且反指标要求 ≤25% |
| 不适合占比 | 12.0% | ≤15% ✅ |
| 一般占比 | 32.0% | — |

**最高分 79.0，差 1 分到 80。**

### 根因（三层叠加）

1. **boost 需求 > 容量**：11 条 boost 的 `delta` 合计 **38 分**，但加分总容量只有 **30 分**（`max_d − base_d` 之和）。这一条在 docs/03 里已被 tech-arch 预判并量化。
2. **有 3 条 boost 在当前语料上无区分度**（见 F-02）→ 实际可用容量更低。
3. **base = 70 偏高**：要到 80 需净赚 +10，而现实优秀搭配通常只触发 4–7 条 boost 并伴随 1–2 条小扣分 → 落在 73–79。

### 可选修法（**需产品决策，未擅自执行**）

| 方案 | 效果 | 代价 |
|---|---|---|
| **A. base 70 → 62，boost 容量 30 → 38**（docs/03 §12.4 推荐） | 打开 8 分上限，强烈推荐可达 | 全链路分数整体下移约 8 分，verdict 分布重排，**必须重跑标注集校准**，且属破坏性变更（需 bump ruleset MAJOR） |
| **B. 阈值 80 → 76** | 改动最小，立刻生效 | 违背 baseline §5.2 的"满分必须是荣誉"，且 76 分显得廉价 |
| **C. 不动** | — | 「强烈推荐」名存实亡，长期是产品缺陷 |

> **我的判断**：选 A。理由：B 会让"强烈推荐"失去区分力，而 A 是唯一同时保住"满分荣誉感"和"可达性"的方案；它的代价（重跑标注集）本来就在 M5 阶段要做。

## F-02 · 34% 的规则在现有解析能力下**无判别力**

### 实测

`scripts/rule_coverage_report.py` 在 10 剧本 × 5 场合上统计每个 DSL 字段的取值多样性：

```
规则总数 50 ｜ 依赖字段缺失 0 ｜ 依赖字段恒定 17（34%）｜ 其中 boost 3
```

"字段恒定"意味着：**该规则所需的信息，当前解析层喂不出来**，所以它在所有样本上表现一致（恒命中或恒不命中）。它不是崩溃，而是**静默失效**——最危险的一类。

### 按根因分两类

**根因 A：解析层缺能力（需要更强的 VLM 输出或几何模型）**

| 缺失量 | 受影响规则 |
|---|---|
| `is_tucked`（上装是否塞入） | R-PROP-001, 002, 009, R-DET-006 |
| `visual_waist_y` / `visual_center_y`（视觉腰线/重心） | R-PROP-004, 005, 009 |
| `hem_pooling`（裤脚是否堆积） | R-PROP-008 |
| `length_ratio` / `area_ratio` / `waist`（长度与面积占比） | R-PROP-001, 005, 007, R-OCC-005 |
| `trend_tag_count`（潮流元素计数） | R-STYLE-007 |
| `metal_hue_span`（金属色色相跨度） | R-COLOR-010 |

> 这些是**人体几何 / 穿着状态**量，单纯"认图说话"的 VLM 给不出来。需要：姿态关键点模型（估计腰线/重心）或让 VLM 输出带 bbox 的结构化结果。

**根因 B：画像层缺字段（用户没声明偏好）**

| 缺失量 | 受影响规则 |
|---|---|
| `forbidden_overlap_count`（禁用风格重叠） | R-STYLE-001（hard！） |
| `conflict_pair_count`（冲突风格对计数） | R-STYLE-004 |
| `explore_overlap_count`（探索风格重叠） | R-STYLE-009（boost） |

> mock 画像永远不产出 `banned_styles` / `explore_tags`，所以**唯一的 hard 风格规则（R-STYLE-001）在 demo 里恒不触发**。修法很轻：画像页让用户勾选"绝对不穿"和"想尝试"即可（这也正好是 PRD 里 P1 的"画像手动修正"）。

### 修法优先级

1. **根因 B 立刻修**（半天）：画像加 `banned_styles` / `explore_tags` 两个用户输入 → 让 1 条 hard + 1 条 boost 复活。
2. **根因 A 分期修**：先补 `length_ratio`/`area_ratio`（VLM 可估），再上姿态模型补腰线/重心。

## F-03 · 余弦类阈值**绑定 embedding 后端**，换后端即失真

### 实测分布（hash embedding）

| 关系 | min | p50 | p75 | max |
|---|---|---|---|---|
| 搭配 ↔ 搭配（两两，n=45） | 0.007 | 0.168 | 0.203 | **0.289** |
| 画像 ↔ 搭配 | 0.281 | 0.445 | — | **0.585** |

### 两个直接后果

1. **锚点阈值 0.60（契约默认）永远不达标** → 锚点功能恒为空。已改为**可配置** `ANCHOR_MIN_SIM`，hash 模式标定为 **0.20**（≈p75），并在 `.env` 里注明"接语义 embedding 后改回 0.60"。
2. **R-STYLE-009 的窗口 `0.60 ≤ cosine ≤ 0.75` 不可达**（实测最大 0.585）→ 该 boost 恒不触发。这正是 F-01 里"3 条 boost 无区分度"的其中一条。

### 根因

`docs/03` 里这些阈值是按**语义 embedding**（如 FashionCLIP）的余弦分布写的；而 demo 用的是**确定性哈希 embedding**（零依赖、可复现），其余弦区间天然被压缩。

### 修法（推荐）

**不要把绝对余弦阈值写进规则。** 两条路：
- **A（推荐）**：在 `derived.cosine_uv` 之前做一次**单调归一化**，把后端相关的余弦映射到稳定的 0–1"风格相似度"（例如按画像自身参考集的分布做 min-max），规则只吃归一化后的值 → 规则阈值与后端解耦。
- **B**：为每个 embedding 后端维护一张标定表（`cosine_thresholds: {hash: {...}, clip: {...}}`），随 ruleset 发布。

> 这也是 F-02 的一个特例：**规则不应该知道 embedding 的实现细节**。

## F-04 · `formality` 的 int(1–5) 与 float(0–1) 量化损失

- `contracts.Garment.formality` 是 **int 1–5**（为了 UI 友好）
- `docs/03` 的规则按 **0.00–1.00** 浮点写（如 `formality_span > 0.50`、`formality_gap ±0.20`）
- 实现按 `(f−1)/4` 映射 → **量化步长 0.25**，远大于 ±0.20 的判定边界

**后果**：R-OCC-003/004（正式度不足/过剩）在边界附近判定不稳定，`formality_span > 0.50` 也只剩 0.5 / 0.75 / 1.0 几个离散取值。

**修法**：契约 v1.1 给 `Garment` 增加 `formality_score: float`（0–1，VLM 直接输出连续值），保留 `formality: int` 作为展示字段。这是**向后兼容的新增**，不破坏现有规则。

## F-05 · 契约的三处缺口（已绕过，建议 v1.1 回填）

| # | 缺口 | 现状 | 建议 |
|---|---|---|---|
| 1 | 无 `bag` slot | 规则需要 `garment.bag.*`；context 用 category 关键词把 `accessory` 拆成 bag/accessory | 要么契约加 `Slot.bag`，要么在 04 文档固化"品类词表 → slot"映射并让 parser 负责 |
| 2 | `Rule` 缺治理字段（`introduced_in` / `deprecated_in` / `status_changed_at`） | `Rule` 是 `extra="forbid"`，写不进 YAML；docs §6.1 要求这些字段 | 契约补 3 个可选字段 |
| 3 | `RuleHit` 无 `suppressed_by` | docs §10.3 要求"被压制的规则保留并标记"，但实现按"丢弃"（否则无字段承载） | 若要支持"解释为什么这条没扣分"，需加字段；MVP 判断是**不需要**（会让报告变噪音） |

另外 **16 组 `[EXT]` 预计算字段**目前只登记在 `src/rules/context.py` 顶部，不在任何契约文档里。建议把 docs/03 §7.7 的预计算字段表**升格为契约附件**——否则下一个实现者会重复走一遍。

## F-06 · 评测只能证明「流水线正确」，不能证明「审美判断正确」（重要）

### 实测（20 套用例）

| 指标 | 实测 | 门槛 | 结论 |
|---|---|---|---|
| 总分 Spearman ρ | **0.7376** (p=0.0002) | ≥0.60 | ✅ |
| Verdict 4 分类准确率 | 65.0% | ≥65% | ✅（刚好压线） |
| 扣分可追溯率 | 100.0%（71 项） | 100% | ✅ |
| 确定性 | 100%（20 套×2 次） | 100% | ✅ |
| 「不适合→强烈推荐」 | 0.0% | ≤5% | ✅ |

### 但必须诚实说明这个数字的**边界**

这 20 套用例是**合成**的：由 mock parser 的 10 个剧本派生，而"人工分"是按剧本设计意图赋予的。**它们验证的是：**

- ✅ 链路能跑通、契约不变量成立、确定性可复现、扣分可追溯
- ✅ 规则的相对排序大致符合设计意图

**它们不能验证：**

- ❌ 真人照片上的识别准确率（mock 不做视觉）
- ❌ 真实审美判断与人类专家的一致性（人工分是"设计者认为"的分，存在循环论证风险）
- ❌ 跨人群的泛化（全部样本来自同一套剧本）

### 修法（M5 必做）

用 `docs/08 §2` 的标注协议，**采集 20 套真实照片 + 3 名盲评标注者**，重跑同一套指标。在那之前，Spearman 0.74 **不应对外引用**。

## F-07 · 实测数据（修正 docs/05 的成本模型假设）

| 项 | 实测 | docs/05 假设 | 影响 |
|---|---|---|---|
| 图像 token（512×512） | **258** | 1024/图 | Qwen 是 32×32 px/token，512² → 256 ✅ 与文档公式一致；但**多数用户会传更大的图**，1024² 才是 1024 token |
| VLM 单图延迟 | ≈ **11 s**（qwen3.7-plus，3 图 34.2s） | 未定 | P95 ≤20s 的预算是**紧的**：单图 11s + 规则 5ms + LLM 2.3s ≈ 13.5s，多图会超 |
| 文本 LLM 合成 | ≈ **2.3 s** | 未定 | 可接受 |
| 规则执行 | **2–5 ms**（首跑 246ms 含预热） | — | 可以忽略，不是瓶颈 |

**结论**：**瓶颈是 VLM 的图像解析，不是规则也不是 LLM**。这反过来印证 docs/05 的"image token 总量是主导变量"——但更准确地说，**是"图的数量 × 解析延迟"**。优化优先级：① 客户端压缩到长边 1024；② 多图并发解析；③ 解析结果缓存（同一图重复评审）。
