# 10 · 实现发现（文档 vs 代码的对比账）

> 目的：设计文档 → 参考实现的过程中，暴露出的**文档没说清、说错了、或实现才知道的问题**。
> 这一页的价值在于：它记录了「文档成立」与「系统可用」之间的差距，而不是粉饰 demo。
>
> 版本：v0.1 ｜ 日期：2026-10-31 ｜ 全部条目均有实测数据支撑

---

## 0. 一句话结论

**demo 已可跑通并演示，但离"可上线"还差三件事**：① 分数上限不可达（F-01）；② 三分之一规则在现有解析能力下无判别力（F-02）；③ 评测集是合成的，不能证明审美判断质量（F-06）。

## F-01 · 「强烈推荐」档在现有规则集下**不可达**（严重）

### 实测

跨 10 个剧本 × 5 个场合（50 组）扫描：

| 指标 | 实测值 | 文档预期 |
|---|---|---|
| 分数范围 | **45.4 – 79.0** | 0 – 100 |
| 跨度 | 33.6 | — |
| 强烈推荐（≥80）占比 | **0.0%** | 应可达，且反指标要求 ≤25% |
| 不适合占比 | 12.0% | ≤15% ✅ |
| 一般占比 | 32.0% | — |

**最高分 79.0，差 1 分到 80。**

### 根因（三层叠加）

1. **boost 需求 > 容量**：11 条 boost 的 `delta` 合计 **38 分**，但加分总容量只有 **30 分**（`max_d − base_d` 之和）。这一条在 docs/03 里已被 tech-arch 预判并量化。
2. **有 3 条 boost 在当前语料上无区分度**（见 F-02）→ 实际可用容量更低。
3. **base = 70 偏高**：要到 80 需净赚 +10，而现实优秀搭配通常只触发 4–7 条 boost 并伴随 1–2 条小扣分 → 落在 73–79。

### 可选修法（**需产品决策，未擅自执行**）

| 方案 | 效果 | 代价 |
|---|---|---|
| **A. base 70 → 62，boost 容量 30 → 38**（docs/03 §12.4 推荐） | 打开 8 分上限，强烈推荐可达 | 全链路分数整体下移约 8 分，verdict 分布重排，**必须重跑标注集校准**，且属破坏性变更（需 bump ruleset MAJOR） |
| **B. 阈值 80 → 76** | 改动最小，立刻生效 | 违背 baseline §5.2 的"满分必须是荣誉"，且 76 分显得廉价 |
| **C. 不动** | — | 「强烈推荐」名存实亡，长期是产品缺陷 |

> **我的判断**：选 A。理由：B 会让"强烈推荐"失去区分力，而 A 是唯一同时保住"满分荣誉感"和"可达性"的方案；它的代价（重跑标注集）本来就在 M5 阶段要做。

## F-02 · 34% 的规则在现有解析能力下**无判别力**

### 实测

`scripts/rule_coverage_report.py` 在 10 剧本 × 5 场合上统计每个 DSL 字段的取值多样性：

```
规则总数 50 ｜ 依赖字段缺失 0 ｜ 依赖字段恒定 17（34%）｜ 其中 boost 3
```

"字段恒定"意味着：**该规则所需的信息，当前解析层喂不出来**，所以它在所有样本上表现一致（恒命中或恒不命中）。它不是崩溃，而是**静默失效**——最危险的一类。

### 按根因分两类

**根因 A：解析层缺能力（需要更强的 VLM 输出或几何模型）**

| 缺失量 | 受影响规则 |
|---|---|
| `is_tucked`（上装是否塞入） | R-PROP-001, 002, 009, R-DET-006 |
| `visual_waist_y` / `visual_center_y`（视觉腰线/重心） | R-PROP-004, 005, 009 |
| `hem_pooling`（裤脚是否堆积） | R-PROP-008 |
| `length_ratio` / `area_ratio` / `waist`（长度与面积占比） | R-PROP-001, 005, 007, R-OCC-005 |
| `trend_tag_count`（潮流元素计数） | R-STYLE-007 |
| `metal_hue_span`（金属色色相跨度） | R-COLOR-010 |

> 这些是**人体几何 / 穿着状态**量，单纯"认图说话"的 VLM 给不出来。需要：姿态关键点模型（估计腰线/重心）或让 VLM 输出带 bbox 的结构化结果。

**根因 B：画像层缺字段（用户没声明偏好）**

| 缺失量 | 受影响规则 |
|---|---|
| `forbidden_overlap_count`（禁用风格重叠） | R-STYLE-001（hard！） |
| `conflict_pair_count`（冲突风格对计数） | R-STYLE-004 |
| `explore_overlap_count`（探索风格重叠） | R-STYLE-009（boost） |

> mock 画像永远不产出 `banned_styles` / `explore_tags`，所以**唯一的 hard 风格规则（R-STYLE-001）在 demo 里恒不触发**。修法很轻：画像页让用户勾选"绝对不穿"和"想尝试"即可（这也正好是 PRD 里 P1 的"画像手动修正"）。

### 修法优先级

1. **根因 B 立刻修**（半天）：画像加 `banned_styles` / `explore_tags` 两个用户输入 → 让 1 条 hard + 1 条 boost 复活。
2. **根因 A 分期修**：先补 `length_ratio`/`area_ratio`（VLM 可估），再上姿态模型补腰线/重心。

## F-03 · 余弦类阈值**绑定 embedding 后端**，换后端即失真

### 实测分布（hash embedding）

| 关系 | min | p50 | p75 | max |
|---|---|---|---|---|
| 搭配 ↔ 搭配（两两，n=45） | 0.007 | 0.168 | 0.203 | **0.289** |
| 画像 ↔ 搭配 | 0.281 | 0.445 | — | **0.585** |

### 两个直接后果

1. **锚点阈值 0.60（契约默认）永远不达标** → 锚点功能恒为空。已改为**可配置** `ANCHOR_MIN_SIM`，hash 模式标定为 **0.20**（≈p75），并在 `.env` 里注明"接语义 embedding 后改回 0.60"。
2. **R-STYLE-009 的窗口 `0.60 ≤ cosine ≤ 0.75` 不可达**（实测最大 0.585）→ 该 boost 恒不触发。这正是 F-01 里"3 条 boost 无区分度"的其中一条。

### 根因

`docs/03` 里这些阈值是按**语义 embedding**（如 FashionCLIP）的余弦分布写的；而 demo 用的是**确定性哈希 embedding**（零依赖、可复现），其余弦区间天然被压缩。

### 修法（推荐）

**不要把绝对余弦阈值写进规则。** 两条路：
- **A（推荐）**：在 `derived.cosine_uv` 之前做一次**单调归一化**，把后端相关的余弦映射到稳定的 0–1"风格相似度"（例如按画像自身参考集的分布做 min-max），规则只吃归一化后的值 → 规则阈值与后端解耦。
- **B**：为每个 embedding 后端维护一张标定表（`cosine_thresholds: {hash: {...}, clip: {...}}`），随 ruleset 发布。

> 这也是 F-02 的一个特例：**规则不应该知道 embedding 的实现细节**。

## F-04 · `formality` 的 int(1–5) 与 float(0–1) 量化损失

- `contracts.Garment.formality` 是 **int 1–5**（为了 UI 友好）
- `docs/03` 的规则按 **0.00–1.00** 浮点写（如 `formality_span > 0.50`、`formality_gap ±0.20`）
- 实现按 `(f−1)/4` 映射 → **量化步长 0.25**，远大于 ±0.20 的判定边界

**后果**：R-OCC-003/004（正式度不足/过剩）在边界附近判定不稳定，`formality_span > 0.50` 也只剩 0.5 / 0.75 / 1.0 几个离散取值。

**修法**：契约 v1.1 给 `Garment` 增加 `formality_score: float`（0–1，VLM 直接输出连续值），保留 `formality: int` 作为展示字段。这是**向后兼容的新增**，不破坏现有规则。

## F-06 · 评测只能证明「流水线正确」，不能证明「审美判断正确」（重要）

### 实测（20 套用例）

| 指标 | 实测 | 门槛 | 结论 |
|---|---|---|---|
| 总分 Spearman ρ | **0.7376** (p=0.0002) | ≥0.60 | ✅ |
| Verdict 4 分类准确率 | 65.0% | ≥65% | ✅（刚好压线） |
| 扣分可追溯率 | 100.0%（71 项） | 100% | ✅ |
| 确定性 | 100%（20 套×2 次） | 100% | ✅ |
| 「不适合→强烈推荐」 | 0.0% | ≤5% | ✅ |

### 但必须诚实说明这个数字的**边界**

这 20 套用例是**合成**的：由 mock parser 的 10 个剧本派生，而"人工分"是按剧本设计意图赋予的。**它们验证的是：**

- ✅ 链路能跑通、契约不变量成立、确定性可复现、扣分可追溯
- ✅ 规则的相对排序大致符合设计意图

**它们不能验证：**

- ❌ 真人照片上的识别准确率（mock 不做视觉）
- ❌ 真实审美判断与人类专家的一致性（人工分是"设计者认为"的分，存在循环论证风险）
- ❌ 跨人群的泛化（全部样本来自同一套剧本）

### 修法（M5 必做）

用 `docs/08 §2` 的标注协议，**采集 20 套真实照片 + 3 名盲评标注者**，重跑同一套指标。在那之前，Spearman 0.74 **不应对外引用**。

## F-07 · 实测数据（修正 docs/05 的成本模型假设）

| 项 | 实测 | docs/05 假设 | 影响 |
|---|---|---|---|
| 图像 token（512×512） | **258** | 1024/图 | Qwen 是 32×32 px/token，512² → 256 ✅ 与文档公式一致；但**多数用户会传更大的图**，1024² 才是 1024 token |
| VLM 单图延迟 | ≈ **11 s**（qwen3.7-plus，3 图 34.2s） | 未定 | P95 ≤20s 的预算是**紧的**：单图 11s + 规则 5ms + LLM 2.3s ≈ 13.5s，多图会超 |
| 文本 LLM 合成 | ≈ **2.3 s** | 未定 | 可接受 |
| 规则执行 | **2–5 ms**（首跑 246ms 含预热） | — | 可以忽略，不是瓶颈 |

**结论**：**瓶颈是 VLM 的图像解析，不是规则也不是 LLM**。这反过来印证 docs/05 的"image token 总量是主导变量"——但更准确地说，**是"图的数量 × 解析延迟"**。优化优先级：① 客户端压缩到长边 1024；② 多图并发解析；③ 解析结果缓存（同一图重复评审）。

## F-08 · 画像区分度只有 5.0 分（门槛 8 分）——**个性化在产品层面尚未成立**（最严重）

### 实测（`scripts/profile_discrimination.py`）

3 个不同人设（通勤知性 / 法式约会 / 运动休闲），10 剧本 × 5 场合 × 3 画像对 = **150 对比较**：

| 指标 | 实测 | 门槛 | 结论 |
|---|---|---|---|
| **画像区分度（中位数）** | **5.0 分** | ≥ 8.0 分 | ❌ **FAIL** |
| 平均差异 | 4.33 分 | — | — |
| P90 / 最大差异 | 9.0 分 | — | 上限只有 9 分 |
| **零差异占比** | **20.0%**（30 对完全同分） | 越低越好 | 这些搭配**对谁都一样** |
| Verdict 分歧率 | 22.7% | — | 唯一的好消息 |

典型失效点：`sport_active` 在 5 个场合下，"通勤知性" 与 "法式约会" 两个画像给出**完全相同的分数**（69.0 / 62.0 / 69.0 / 58.2 / 65.0）。

> 这正是 docs/08 §3.1 预言的死亡线：**区分度 < 8 分，系统退化成通用审美打分器，产品价值归零**。也就是 docs/06 调研里 40 个失败 App 的同款结局。

### 根因：个性化被结构性锁死在 25% 权重里

| 事实 | 数字 |
|---|---|
| 直接读 `profile.*` 的规则 | **1 条 / 50**（只有 R-STYLE-002） |
| 与画像相关的维度 | 只有 **D2 风格一致性**（权重 25%） |
| 与画像无关的维度 | D1+D3+D4+D5 = **75%** |
| D2 内可用的画像相关规则 | 4 条（R-STYLE-001/002/008/010），其中 **R-STYLE-001 因画像无 `banned_styles` 恒不触发** |

**推论（可手算验证）**：D2 的基准 18 分，最多扣到 0 / 加到 25，理论摆动 25 分；但现实中只有 -5（无交集）+4（命中 top-1）+3（三件同源）这几条会动，实际摆动 **5–9 分** —— 与实测中位数 5.0、最大值 9.0 **完全吻合**。

这不是 bug，是**模型设计的结构性后果**：如果一个系统 75% 的分数与用户无关，它给所有人的分数自然差不多。

### 修法（按性价比排序）

| 优先级 | 动作 | 预期效果 | 成本 |
|---|---|---|---|
| **1** | **画像补 `banned_styles` / `explore_tags`**（用户勾选"绝对不穿"/"想尝试"） | 让唯一那条 hard 风格规则复活 → 一次 veto 就是 20+ 分差异 | 半天 |
| **2** | **新增 profile-conditioned 规则族，铺到 D1/D3/D4/D5**（12–16 条）：<br>· 色彩偏好（画像色温偏冷 vs 搭配偏暖）<br>· 比例习惯（画像惯用高腰 vs 本套低腰）<br>· 场合偏好（画像常穿场景 vs 声明场景）<br>· 配饰密度（画像极少用配饰 vs 本套过多） | 把可摆动区间从「25% × 0.2」提到「接近 100% × 0.15」 | 3–5 天 |
| **3** | 提高 D2 权重 25 → 30 | 治标，且破坏固定权重契约 | 不推荐 |

> **必须先做 1 和 2，再谈 F-01（上限不可达）。** 理由：F-01 让"最高分不够高"，F-08 让"分数与用户无关"——后者直接否定产品命题。先修 F-08，再做 F-01 的 base 重标定，可以一次性重跑标注集，省一轮成本。

### 验收口径（修完必须重测）

- 画像区分度中位数 **≥ 8 分**（docs/08 §3）
- 零差异占比 **< 5%**
- Verdict 分歧率 **≥ 25%**（个性化应能改变结论，而不只是改小数点）
- 同时确认 Spearman **不下降**（个性化不能靠牺牲准确性换）

## F-09 · 首轮标定（ruleset `rs-2026.10.2`）—— 修掉误伤 + 解除死规则

### 改了什么（**改的是误报与后端标定，不是调参凑分**）

| 规则 | 原问题 | 修法 | 依据 |
|---|---|---|---|
| R-COLOR-006 明度断层 | 把「黑白高对比」判成"生硬切断"，正装/中性色经典手法被误罚 | 加豁免：上下装同为中性色、或正式场合时不罚 | 黑白对比是剪裁手法 |
| R-DET-003 季节材质冲突 | 衬衫(棉)+羊毛西装被判"季节冲突" | 加豁免：有层次（`layer_depth ≥ 2`）时冬夏混搭正常 | 叠穿本来就冬夏混穿 |
| R-STYLE-003 单品不同源 | 正装是制服式组合，用 style_tags jaccard 衡量会系统性误判 | 加豁免：`formality ≥ 0.85` 时该规则不适用 | 同源由品类保证 |
| R-STYLE-005 风格偏移 | 阈值 0.55 在 hash embedding 下误罚约 70% | 0.55 → **0.35**（≈p10） | F-03 后端标定 |
| R-STYLE-009 画像内探索 | 窗口 0.60–0.75 高于观测上界 0.585，**永远不可能触发** | 0.60–0.75 → **0.45–0.58** | F-03 后端标定 |

契约同时升版：`CONTRACT_VERSION 1.0.0 → 1.1.0`（新增 `Report.recall`、`StyleProfile.explore_tags`、`CreateProfileRequest.banned_styles/explore_tags`；均为向后兼容新增）；规则集 `rs-2026.10.1 → rs-2026.10.2`。

### 效果（同一套 20 用例评测 + 150 对区分度）

| 指标 | 标定前 | 标定后 | 变化 |
|---|---|---|---|
| 总分 Spearman ρ | 0.7376 | **0.8557** | ▲ +0.118（p=0.0000） |
| 分数范围（50 组扫描） | 45.4 – 79.0 | **36.4 – 81.0** | 跨度 33.6 → 44.6 |
| **强烈推荐占比** | **0.0%（不可达）** | **4.0%（可达）** | ✅ **F-01 解决** |
| 不适合占比 | 12.0% | 20.0% | ⚠️ 略超 ≤15% 反指标（因启用了禁用风格） |
| 正装误伤（c13） | 64.0「一般」 | **76.0「适合」**（人工 86） | 偏差 −22 → −10 |
| 扣分可追溯率 / 确定性 | 100% / 100% | 100% / 100% | 未退化 |
| 画像区分度（无偏好） | 5.0 分 | **5.0 分** | 未改善（需 F-02） |
| **画像区分度（带偏好）** | — | **8.0 分 ✅ PASS**（verdict 分歧 50%） | 新能力生效 |

### 关键结论：**F-01 不需要改 `base_score`**

原方案建议 base 70→62 才能让"强烈推荐"可达。但**先修误伤 + 复活死规则**后，优质搭配自然能上到 81 分，`base_score` 保持 70 不用动。

> 可复用经验：**上限不可达时，先查是不是有规则在错误扣分、或有 boost 规则根本没生效**，再考虑动基准分。动 base 是破坏性变更（要重跑全量标注），修误伤只是修 bug。

### 画像区分度：能力已就绪，但**必须让用户声明偏好**

| 条件 | 中位数 | verdict 分歧率 | 判定 |
|---|---|---|---|
| A 纯统计画像（只有参考穿搭） | 5.0 分 | 32% | ❌ FAIL |
| B 带主观偏好（`banned_styles` / `explore_tags`） | **8.0 分** | **50%** | ✅ PASS |

**产品含义（重要）**：冷启动用户（不填偏好）的区分度只有 5.0 分，接近通用打分器；一旦声明"绝对不穿/想尝试"，立刻到 8.0 分，且一半场景会改变结论。
→ **画像页必须主动引导用户填这两项**，这不是可选加分项，而是产品命题成立的前提。建议把"这 3 个风格我绝对不穿"做成画像流程的必答步骤。

### 仍未解决（按优先级）

1. **F-02（34% 规则无判别力）**：依赖人体几何量（腰线/重心/塞衣角）的规则需要姿态模型；依赖 `trend_tag_count` / `explore_overlap_count` 的需要更丰富解析。这是把区分度从 8.0 继续推高、把 verdict 准确率从 65% 推上去的主路径。
2. **Verdict 准确率 65.0%（压线）**：瓶颈在 D1/D3 的细节量不足，不在权重。
3. **不适合占比 20% 超过 ≤15% 反指标**：启用禁用风格后必然上升，需在默认（无偏好）路径复测。

## F-10 · 人形检测与主体裁剪（v1.2）—— 背景不是风险，**遮挡才是**

### 实测（3 变体，真 key，同一套藏青上装+燕麦下装+黑鞋）

| 变体 | 单品数 | 主色偏差（每通道最大差） | 背景误判 |
|---|---|---|---|
| A 干净平铺 | 3/3 | 9 / 4 / 1 | 无 |
| B 人物 + 杂乱室内（窗/挂画/绿植/椅/地毯） | 3/3 | **1 / 8 / 0** | 无，且主动列出 `bg_ignored: [窗户,挂画,植物,桌子]` |
| C 遮挡（包挡腰）+ 下半身裁切 + 第二人 | 2–3/3 | 9 / **159** ✗ | 无，但**把包的颜色当成了下装** |

**三条结论**：
1. **背景杂乱不是主要风险** —— VLM 自己就能忽略，别为它过度工程。
2. **遮挡是真风险** —— 而且模型自评 `occluded: false` 不可信（实测说了 false，实际被挡）。
3. **裁切会静默产生残缺判断** —— 鞋不在画面里，系统照样给强判断。

### 已实现（`src/parsing/person_crop.py`，可插拔三后端）

| 后端 | 触发条件 | 说明 |
|---|---|---|
| `onnx` | `models/yolov8n.onnx` 存在 | YOLOv8 单类 person + NMS，取面积最大者；**离线、最稳**（未随仓库分发权重） |
| `vlm` | 有 key 且在线 | 用 VLM 做 grounding 返回 bbox（**已自动修像素/归一化坐标歧义**） |
| `none` | 离线兜底 | 原图直送 |

配套的**输入质量门**：多人 −0.25 / 非全身 −0.25 / 主体过小 −0.30 / 遮挡 −0.15，
以及解析后反向校验（`INCOMPLETE_NO_SHOES_MAYBE_CROPPED` −0.20）。
质量分以 `SUBJECT_QUALITY:x` 进入 `parse_warnings`，由 `compute_assessability` **统一压低五个维度**——
这才是「证据不足不下判断」的落地，而不是靠模型自评。

### 效果与残余风险

- B：裁剪后识别出主体框（area 0.518），并**主动报告遮挡物**（"前景的椭圆形桌子遮挡了小腿"）→ 质量 0.85
- C：裁剪后仍把包识别成下装（`lower=#5D4037`，偏差 147）—— **裁剪解决不了"挡在身体前面的东西"**
- A（平铺）：正确报告"无人物" → 质量 0.85（平铺是合法输入，不该按"证据不足"重罚）

**残余风险与后续**：
- 遮挡需要「单品 bbox 交叉校验」（两个单品落在同一区域 → 冲突降级），或让用户补一张无遮挡图；
- 多人物在真实合照上的表现未验证（当前只有合成的灰度第二人）；
- 建议把 `yolov8n.onnx` 作为可选制品随部署分发，替换 VLM grounding（省一次调用、更稳定）。

## F-11 · 真视觉编码替换「伪视觉」哈希（v1.2）

### 原问题（重要坦白）

原 `img_emb` 是**搭配文本签名的 sha256 伪随机单位向量**：确定性、可复现，但**零视觉语义**。
256 维里真正带语义的只有 96 维结构化特征，所以：

- 余弦被压缩在 **0.007 – 0.29**（两个"指纹"之间本就近似随机）
- 锚点阈值、`R-STYLE-005/009` 的阈值全部失真（F-03）
- "双塔"名不副实：只能算"描述像不像"，算不出"视觉像不像"

### 现状（FashionCLIP · ONNX Runtime，**不需要 torch**）

| 项 | 值 |
|---|---|
| 模型 | `patrickjohncyh/fashion-clip`（CLIP ViT-B/32 时尚域微调），512 维 |
| 推理 | onnxruntime CPU；**首次建 session 2.9s，之后 0.1s/张** |
| 权重 | `onnx/model.onnx` **606 MB**（`git` 忽略，用 `scripts/fetch_fashionclip.py` 拉取） |
| 下载通道 | 官方 HF 被墙 → **hf-mirror.com** 可达（2.9 MB/s，约 3.5 分钟）；且必须带浏览器 UA，否则 403 |
| 指纹 | 模型 sha256 + 预处理 mean/std + 512→160 投影 sha256 全部进 `encoder.manifest()` |

**实测余弦分布（7 张图两两）**：min 0.506 / p50 0.738 / max 0.926 —— 与哈希的 0.007–0.29 完全不同量级。

### 关键设计：**余弦必须按后端归一化，否则规则阈值立刻失效**

视觉后端给 0.79 的"同一套风格"，规则阈值却按哈希写死 0.35 / 0.45–0.58 → 全部失灵（F-03 复发）。
已实现 `calibrate_style_cosine(raw, backend)`：为每个后端定义两个锚点（"同一套"的典型余弦、"明显不相关"的典型余弦），
线性映射到统一刻度后再喂规则。

- 视觉：0.95 → 0.95（自身），0.62 → 0.22（无关），0.77 → 0.55（中等）
- 哈希：**恒等**（保持既有评测不变）
- 验证：`commute_polished` 校准后 0.828 无风格扣分；`color_clash` 0.501 触发"无交集"类规则

### 空间一致性（踩过的坑）

双塔要求两侧**同后端**。用户侧是真实人像 → FashionCLIP；库条目只有属性 → 若仍用哈希，
两边不同源、cosine 无意义。已处理：

- 库条目用 `render_outfit_image()` 渲染成「人穿着这套」的示意图再算视觉向量（12/12 成功）
- `LibraryIndex(allow_visual=...)`：离线/mock 时**整库强制哈希**，绝不混用（实测 `visual_used=False`）
- 自校验：用库条目自身查询，第一名 = 自身 1.000，相似条目 0.82–0.83 ✓

### 仍未解决
1. **库条目是渲染图不是真人照** —— 与真实查询图存在域差；生产必须换成真实搭配图。
2. 视觉锚点（0.95 / 0.62）来自 **7 张合成图**，样本太少；换真实照片后需重新标定。
3. 离线路径仍是哈希（评测与 182 项测试保持不变，这是刻意为之，保证可比与零依赖）。

## F-12 · 参考穿搭「越多越好」是错的：3–5 张最优，更多会**稀释**画像

### 实测（`scripts/profile_size_ablation.py`，10 套风格互异的搭配按多样性递增加入）

| n | 置信度 | top1 权重 | 与全量画像余弦 | verdict 一致率 | 平均分差 |
|---|---|---|---|---|---|
| 1 | 0.41 | **0.601** | 0.528 | 90% | 4.20 |
| 2 | 0.54 | 0.484 | 0.663 | 95% | 3.50 |
| 3 | 0.66 | 0.323 | 0.762 | **95%** | 2.85 |
| 4 | 0.78 | 0.242 | 0.828 | 85% | 3.35 |
| 5 | **0.90** | 0.194 | 0.877 | 85% | 2.10 |
| 6 | 0.90 | 0.161 | 0.921 | 85% | 1.95 |
| 8 | 0.90 | 0.168 | 0.968 | 85% | 3.25 |
| 10 | 0.90 | **0.151** | 1.000 | 100% | 0.00 |

边际信息增益（加入第 n 张时画像相对上一版的变化余弦）：0.779 → 0.879 → 0.920 → 0.938 →
**0.957 → 0.970 → 0.973 → 0.978 → 0.991**。

### 三条结论

1. **置信度在第 5 张饱和**（0.41→0.66→0.90，之后不再上升）。第 6 张起边际增益 <5%。
2. **标签极化单调崩塌**：top1 权重 0.601 → 0.151（降到 1/4）。因为我们用的是**无加权平均**，
   参考集越杂，"你是什么风格"越被平均成"平均人"——这正是 F-08 区分度不足的放大器。
3. **verdict 一致率不单调**：90% → 95% → **85%（n=4、5）** → 100%。说明加照片**会改变结论**，
   而且方向不保证更好。多不等于准。

### 稀释实验（同一批探针，只换参考集构成）

| 参考集 | 极化度(top1−top3) | 探针分数极差 |
|---|---|---|
| 3 张同类（通勤/极简/正装） | 0.152 | **20.8** ← 最能区分 |
| 3 张混杂（通勤+运动+撞色） | 0.281 | 13.0 |
| 6 张混杂 | **0.032** ← 最扁平 | 15.8 |

**关键洞察：3 张同风格的区分力（极差 20.8）优于 6 张混杂（15.8）。**
参考集的**纯度**比**数量**更重要。

### 为什么限 10 张（真实理由，按重要性排序）

| # | 顾虑 | 量化 |
|---|---|---|
| 1 | **成本/延迟线性增长** | 每张 = 1 次 VLM 调用（≈11s、768 tokens）。10 张 ≈ 110s、7,700 tokens，用户会以为卡死 |
| 2 | **稀释效应**（上面实测） | >5 张后 top1 权重继续下滑，个性化被平均掉 |
| 3 | **污染无抵抗力** | 当前是等权平均，1 张误识别（如包被当裤子、F-10 的遮挡问题）就能拽偏画像，且**没有离群点剔除** |
| 4 | 契约层护栏 | `CreateProfileRequest.image_refs` 的 `MaxLen(10)`，11 张直接 422：`List should have at most 10 items` |

> 这 10 是**产品护栏，不是技术墙**。放开到 20 不会崩，但会同时放大稀释与污染——
> 所以正确顺序是：**先做加权/剔除，再放开上限**。

### 建议（比「提高上限」更值得做）

1. **推荐用户传 3–5 张**，且**同一风格主线**（例如都是通勤/极简），而不是"每种风格各来一套"。
2. **加权平均**替代等权：权重 = 图像质量分（`SUBJECT_QUALITY`）× 解析置信度 × 时间衰减；
   对与画像中心余弦过低的离群参考降权（等价于简单离群剔除）。
3. **分场景画像**（通勤画像 / 约会画像 / 运动画像）而不是一个大杂烩画像——
   这能同时解决稀释与"场景适配"（D4）的精度问题。
4. 上限可在 `CreateProfileRequest` 里调，但应**先落地 2 和 3**再调。

## F-13 · 静默降级：把「占位标识」当照片，会拿到一份假数据报告（已加硬保险）

### 现象

用户贴了 8 个参考标识，页面返回了完整的画像（10 个风格标签 + 每个标签的 `oft_xxx` 证据），
但解析告警里是：

```
VLM_SKIPPED_NO_FETCHABLE_IMAGE_FALLBACK_MOCK；VLM_MODEL:qwen3.7-plus   （重复 8 次）
```

### 这是什么

**不是报错，是"没在解析你的照片"**：8 个标识没有一个能解析成真实图片文件
（既不是已存在的本地文件，也不是 http(s) 或 data URI），所以系统跳过了真实 qwen3.7-plus，
**用 mock 生成了 8 套虚构搭配**。页面上的标签与 `oft_` 证据全部来自这些假搭配，
与用户照片无关。

`VLM_MODEL:qwen3.7-plus` 同时出现，说明 key 与在线模式都正常——问题只在**路径**。

### 根因

`QwenVLMParser.parse_outfit` 里有一条"快速失败"守卫：为了不给演示标识白付两次超时与计费，
若所有 ref 都不可 fetch，就直接降级 mock。这个设计是对的（省时省钱），
但**降级太安静**：只在 `parse_warnings` 里留一行，用户很容易把假画像当真。

触发方式（实测复现）：直接使用 UI 文本框里预填的 `demo/commute-1` 之类的占位标识。

### 已修（4 处加固）

| # | 改动 | 效果 |
|---|---|---|
| 1 | `ReportMeta.data_source: "vlm" \| "mock"` | 报告**自己声明**数据来源；只要解析走了 mock 就标 `mock` |
| 2 | 前端红色横幅 | `data_source == mock` 时在报告顶部明示"这份报告不是基于真实照片，不能用来判断系统好坏" |
| 3 | 告警去重计数 | `VLM_MODEL:qwen3.7-plus ×3`，让关键信息不被 16 行重复告警淹没 |
| 4 | 告警带诊断 | `..._FALLBACK_MOCK:refs=1:sample=demo/commute-1:hint=not_a_file_or_url`，直接指出是哪个标识、为什么被拒 |

实测两种输入：

```
A 占位标识 : data_source=mock   total=78.0   ← 假数据（分数看似"很好"，但没有意义）
B 真实图片 : data_source=vlm    total=47.2   verdict=unsuitable   ← 真实结论
```

> 值得注意：A 的 mock 数据反而给出 78 分「适合」，比真实图片的 47.2 分漂亮得多。
> **假数据往往更"好看"**，这正是必须显式标注来源的原因。

### 给使用者的判定口诀

看到 `data_source=mock` 或 `VLM_SKIPPED_NO_FETCHABLE_IMAGE` → **立刻停下**，
用 `scripts/check_photo.py` 预检路径，别拿这份报告下任何结论。

## F-14 · 带引号的路径 → 又一次静默降级（实测用户真实踩坑）

### 现象

用户按「复制文件地址」粘贴：

```
"E:\Chuang_Yi_skill\user_picture\1.jpg"
```

告警：`VLM_SKIPPED_NO_FETCHABLE_IMAGE_FALLBACK_MOCK:refs=1:sample="E:\...\1.jpg"`

**引号成了字符串的一部分** → `Path('"E:\...\1.jpg"').is_file()` 恒为 False →
5 张真实照片全被判"不是图片" → 又一次静默降级 mock。

### 根因

`_clean_refs` 只做了 `str(r).strip()`，没有处理引号。而 Windows 资源管理器
「复制文件地址」默认就带双引号——这是最常见的粘贴方式，不是边缘 case。

### 已修

`BaseParser.normalize_ref` 统一归一化：

| 输入形态 | 输出 |
|---|---|
| `"E:\a\1.jpg"` / `'E:\a\2.jpg'` / `“E:\a\7.jpg”` | 去引号 |
| `  E:\a\2.jpg  ` | 去首尾空白 |
| `file:///E:/a/5.jpg` | 去协议前缀 |
| `""E:/a/6.jpg""` | 最多剥 3 层 |

回归测试 8 条参数化 + 带引号真实文件的端到端断言。实测用户 5 张照片：
`data_source=vlm`、5/5 拿到视觉向量、无降级告警。

## F-15 · `str(Verdict.suitable)` 是 `'Verdict.suitable'`，判定词静默退化成「一般」

### 现象

报告里 `verdict=suitable`，但总评写「这套搭配得 76 分（**一般**）」。

### 根因

`Verdict` 是 `(str, Enum)`，Python 的 `Enum.__str__` 返回 `'Verdict.suitable'`，
**不是** `'suitable'`；而 `.value` 才是 `'suitable'`。
任何 `VERDICT_CN.get(str(verdict))` 的查表都会落空 → 默认值「一般」。

同一根源还导致：`llm.py` 曾把枚举直接当 `verdict_cn` 传给模型，
模型于是写出「判定为 suitable」（详见 F-13 的修复）。

### 已修

新增 `templates.verdict_key(value)`：优先取 `.value`，兼容 `'Verdict.xxx'` 字符串，`None` → `neutral`。
`build_summary` / `check_facts` / `llm._build_payload` 全部改用它；
并加 `sanitize_verdict_terms()` 兜底替换模型输出里的英文枚举（长词优先）。

实测：`verdict=suitable` 且总评「判定为适合」，一致。

> **教训（可复用）**：`(str, Enum)` 混血类型的 `str()` 与 `.value` 不等价。
> 只要是拿枚举去查表/拼字符串，就必须显式 `.value`，或写一个 `xxx_key()` 收口。
