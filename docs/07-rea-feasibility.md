# 07 · REA 逆向可行性评估

> 回答第三个问题：**「我能否通过 REA 逆向复刻一份？」**
> 本文不是理论推演，全部结论基于本轮**实际动手**的结果（见 §2 与 §9 的原始记录）。

版本：v0.1 ｜ 日期：2026-10-31 ｜ 状态：待评审

---

## 0. 结论先行

**三句话：**

1. **技术上能干，且本机已跑通。** REA 工具链（Chrome + CDP + `analyze_web_bundle`）在本环境实测可用，能对真实竞品站点做静态 bundle 分析。
2. **但这个品类逆向二进制的 ROI 很低。** 因为产品的价值不在客户端，而在**服务端 prompt + 规则库**。实测证明：竞品 Web 端的可分析面只有营销页，应用逻辑拿不到。
3. **真正的"复刻"路径不是逆向，是 OSINT + 学术复现 + 自建规则。** 本轮已经用合法手段拿到了**比逆向二进制更有价值的东西**：一份完整的专家级 styling prompt 全文、一个竞品的完整评分权重表、以及可直接复现的学术基线。

> **一句话建议**：不要花两周去逆向，花两天做情报，剩下的钱花在规则库和评测集上。

## 1. 先定义"复刻"：你想要的到底是哪一层？

把「一个 AI 穿搭产品」拆成 6 类资产，逐一判定可复刻性——这是判断 ROI 的唯一正确框架：

| # | 资产 | 实际在哪 | 可复刻性 | 正确获取方式 |
|---|---|---|---|---|
| A1 | **交互形态 / UI / 信息结构** | 客户端 | **高** | 观察 + 截图，功能不侵权 |
| A2 | **评分维度与权重** | 混合（常被写进文案/公开 prompt） | **高** | OSINT（商店描述、官网、公开 prompt） |
| A3 | **Prompt 文本** | 服务端（偶见客户端） | **中** | OSINT 优先；客户端仅在架构外露时可得 |
| A4 | **规则库 / 专业判断知识** | 服务端 + 人脑 | **低** | 逆向不到，只能自建或买专家 |
| A5 | **模型权重** | 厂商 | **不可能** | 无 |
| A6 | **用户数据 / 风格画像资产** | 厂商 | **不可能** | 无 |

**关键判断**：A1+A2 是"看起来像"的全部，且**都能通过合法手段拿到**；A4 才是"用起来好"的根本，且**逆向根本拿不到**。

> 很多人以为逆向能拿到"秘密"，其实拿到的是 A3。而 A3 在 2026 年已经越来越公开——因为一批产品主动把 prompt 当获客工具发布（见 §4.1）。

## 2. 本轮实测：REA 工具链验证

### 2.1 实测环境与方法

| 项 | 值 |
|---|---|
| 被测目标 | `https://trydressed.com/`（DRESSED，市场调研认定的 2 号逆向候选，纯 Web 免登录产品） |
| 浏览器 | Chrome **156.0.8078.74**，headless=new |
| 接入方式 | CDP `http://127.0.0.1:9333`（Playwright/DevTools 协议） |
| 分析方法 | `analyze_web_bundle`（静态解析，**不执行**页面 JS） |
| 网络条件 | 本机 fake-IP DNS（198.18.0.0/15），web_fetch 被 SSRF 策略拦截，但系统 HTTPS 正常 |

### 2.2 实测结果

```
scripts_observed : 6
scripts_analyzed : 6
parse_failures   : 0
AST nodes visited: 1396
completeness     : complete
total JS bytes   : ~11.6 KB
routes           : []   ← 空
endpoints        : []   ← 空
source maps      : 未发现
```

单个脚本体积：598B / 413B / 2635B / 6331B / 876B / 770B

### 2.3 这个结果说明了什么

**三个诚实结论：**

1. **工具链没问题。** 完整捕获、零解析失败、AST 全量遍历，能力是真实的。
2. **可分析面很薄。** 全部 JS 只有 11.6KB——这是一个**静态营销页**，不是应用本体。没有路由表、没有 API 端点候选、没有 source map。
3. **应用逻辑不在客户端。** "上传照片 → 打分" 这条链路跑在服务端；客户端只负责发请求和渲染。**逆向客户端永远拿不到评分逻辑。**

> 这正是这个品类的结构性特点：**它的护城河是服务端的 prompt 与规则，而不是客户端代码。** 逆向工程最适合的目标是"逻辑外露到客户端"的软件（如某些桌面软件、游戏、单机 App），而这个品类恰好相反。

## 3. 候选目标可行性矩阵

| 目标 | 形态 | 客户端可获取性 | 逻辑是否在客户端 | 预期能拿到 | 风险 | 结论 |
|---|---|---|---|---|---|---|
| **Cladwell Web**（`app.cladwell.com`） | **纯 Web，标准 Next.js SPA** | **最高**（HTTP 200 直连，无需 APK/IPA） | 部分（Next.js 有 `__NEXT_DATA__` 与客户端 chunk；色彩判定阈值可能在服务端） | 画★像→搭配的产品化结构、路由、状态字段、`__NEXT_DATA__` 里的初始 props | **中高（在营付费产品，ToS/法律）** | ⭐ **P0 首选，见 §3.1** |
| **Modebase** | Web + GPT/Claude 插件 | **直接可读** | **是（主动公开）** | **完整专家级 prompt 全文** | **无** | ✅ **P0 已完成，见 §4.1** |
| **穿搭日记** | iOS only + Next.js 官网 | 官网可抓 / App 需 iOS 包 | 否 | 评分维度与权重（已从商店页取得） | 低 | ✅ **P0 已完成，见 §4.2** |
| **DRESSED** | 纯 Web 免登录 | 高（已实测） | **否（服务端）** | 仅营销页 JS | 低 | ✅ P1 实测完成，**价值低** |
| **Endam** | iOS + 静态官网(endamai.com) | 中 | 否 | 官网为纯静态营销页（已探测：单 script.js + styles.css） | 低 | ⏸ P2，价值低 |
| **BrutalCoach** | Android APK | 中（需找 APK 镜像） | 中（免费次数计数常在客户端） | 请求结构、部分提示词 | 中（混淆 / SSL pinning） | ⏸ P2 |
| **穿啥** | 微信小程序 | 中（wxapkg 需解包） | **中-高**（单人开发 + 大模型 API 的架构，常把 prompt 直接放前端） | **有可能拿到 prompt 与维度** | 中高（包加密、平台条款、合规） | ⚠️ **唯一值得动手的二进制目标** |
| 淘宝 / 京东 / 得物 / 安踏 / Doppl / ASOS | — | 低 | 否 | 无 | **高（法律/平台条款/商誉）** | ❌ **不要碰** |

**排序逻辑**：`OSINT 可得性 × 逻辑外露程度 ÷ 法律风险`。Modebase 与穿搭日记在分子上极高、分母为零，所以已完成；**Cladwell 是"逻辑外露"这一项最强的目标**（唯一纯 Web 且与「画像→搭配」同构）。

### 3.1 为什么首选 Cladwell 而不是那几款打分类 App

市场调研（[06-market-scan](./06-market-scan.md) §9）把 Cladwell 的 Web 版列为首选，理由与我们 §2 的实测结论完全一致：

| 判据 | 打分类 App（穿搭日记 / Endam / Outfitly） | Cladwell Web |
|---|---|---|
| 取证成本 | 需 APK/IPA，且本次 **APKPure/APKCombo/apk.support 全部 403 或 TLS 中断，一个包都没拿到** | **HTTP 200 直连**，零取证成本 |
| 还剩什么可挖 | 评分维度**已从商店页完整拿到**，剩下的只有 prompt | 画像→搭配的**产品化结构**（状态机、字段、路由）仍未公开 |
| 挖到有用吗 | ❌ prompt 不能回答「这个维度该给几分」——而这才是我们的真问题 | ✅ 能回答「画像如何被组织成可用于评审的结构」 |

> **结论**：逆向的价值不在「拿到 prompt」，而在「拿到别人如何把画像工程化」。这一条判断直接改变了投入方向——**不要逆向打分类 App，要去读 Cladwell 的结构**。
>
> 同时，Style DNA 的 `12 色季 × 8 体型 × 6 风格类型` taxonomy 是规则引擎最好的外部知识源，但它疑似来自形象顾问体系的授权内容（IP），**只能当知识地图对照自建，不能做内容复制**。

## 4. 本轮实际拿到的情报（这才是真正的产出）

### 4.1 Modebase 公开的完整 styling prompt —— 一次免费的"专家知识交付"

Modebase 把其 stylist prompt **全文公开在官网**（无需邮箱、无需登录），作为获客工具。

**它的结构（逐段拆解）：**

| 段落 | 内容 | 对我们的价值 |
|---|---|---|
| 总则 | "Work only from what you can actually see in my photo, never from a generic template, and **never flatter me by default**" | ★★★ **反谄媚约束**——正是我们在 PRD P1「判断优先于灵感」里的原则，被竞品用一句 prompt 表达。可直接借鉴这个**表达方式** |
| STEP 1 读人 | 输出 Frame（整体身形、长度分布、肩腰胯腿的平衡）与 Direction（3-4 个诚实的风格词） | ★★★ **把"身形"做成结构化中间产物**，而不是让模型直接给结论 |
| STEP 2 上半身 | 挑选最能扬长避短的领型与上装廓形，每条给"为什么适合**我**" | ★★★ 规则化的写法："领型 → 适配理由"正是我们 COLOR/PROPORTION 规则的表达范式 |
| STEP 3 下半身 | 腰位、腿型、下摆长度，并指出"哪一种长度会显矮" | ★★★ 负向规则（"哪一种会显矮"）——我们的 hard rule 思路一致 |
| 衣橱 schema | `序号 \| 品类 \| 颜色 \| 面料 \| 版型 \| 正式度 \| 品牌` | ★★★ **可直接借鉴的 Garment 最小字段集**，比我们 baseline §2.1 更精简，可作 MVP 字段基线 |
| 缺件处理 | "if a look needs something I do not own, list it under **Missing** instead of pretending" | ★★ **反幻觉机制**——要求模型显式声明缺失，而不是拿相近单品硬凑。这一条应当写进我们的 prompt 契约 |
| 生成约束 | "Keep my real face, hair and body… do not slim me, lengthen me, or smooth me" | ★ 我们 MVP 不生成图，暂不需要，但二期做试穿时必用 |

**必须注意的一点**：这份 prompt 里嵌入了**强制的商业导流话术**（要求模型在首条回复原样输出"去连接我的衣橱"的广告块）。这提醒我们两件事：

1. **公开的 prompt 不等于干净的 prompt**——直接搬运会把别人的商业植入带进你的产品。
2. 从产品设计看，这是一种极致的 PLG（把产品塞进用户的 prompt 里）。**值得学的不是文案，是这个"寄生在通用模型里做分发"的策略。**

### 4.2 穿搭日记的评分权重 —— 从商店文案反推出的竞品 rubric

从 App Store 页面描述**逐条抄录**（原文）：

> - 整体协调性（3分）
> - 时尚度（2分）
> - 场景适配度（2分）
> - 细节质感（2分）
> - **个人辨识度（1分）**
>
> 满分 10 分。等级：满分穿搭 / 优质穿搭 / 中等穿搭 / 基础穿搭 / 需优化

**与我们的设计对比（这是定位差异的量化证据）：**

| 维度 | 穿搭日记权重 | 我们的权重 | 差异解读 |
|---|---|---|---|
| 整体协调性 | 30% | D1 色彩 20% + D3 比例 20% = 40%（拆分） | 我们更细 |
| 时尚度 / 风格一致性 | 20% | **D2 风格一致性 25%** | **我们把"像不像你"提到最高** |
| 场景适配度 | 20% | D4 场合 20% | 一致 |
| 细节质感 | 20% | D5 细节 15% | 略低（因 VLM 细节识别置信度低） |
| **个人辨识度** | **10%** | 融入 D2（25%） | **★ 关键差异：竞品把"个人化"压到最低权重** |

**这张表就是我们的战略依据**：市面第一梯队的穿搭打分产品，把"个人辨识度"给了 10 分——它本质上是**通用审美打分器**，只是留了 1 分的个性化。我们把"风格一致性"提到 25% 并配双塔召回，做的是**真正以个人为基准的评审**。这不是话术差异，是档位差异。

### 4.3 可直接复现的学术基线（不需要逆向任何人）

| 工作 | 类型 | 一句话价值 |
|---|---|---|
| **Polyvore + Type-Aware Embeddings** (arXiv 1803.09196) | 数据集 + 方法 | 穿搭兼容性的开山基准，定义了"兼容性"如何量化 |
| **FashionCLIP** (arXiv 2204.03972) | 模型 | 领域自适应 CLIP，**可直接作为我们双塔的图像编码器底座** |
| **FashionStylist** (arXiv 2604.09249, 2026) | 数据集 + 评测 | 带专家标注的 outfit evaluation，**与"千条规则"最同构** |
| **Loom** (arXiv 2605.09830, 2026) | 架构 | 检索-打分两段式 + 材质兼容 + 场合先验，**结构上就是双塔召回+打分** |
| **MCN** (arXiv 1907.11496) | 方法 | 兼容性**诊断**（不只是打分，还能指出冲突在哪），与我们的 `rule_hits` 思路一致 |
| **NGNN** (arXiv 1902.08009) | 方法 | 图神经网络建模单品关系 |
| **OutfitTransformer** (arXiv 2204.04812) | 方法 | Amazon 出品，outfit 级 Transformer 编码 |

> **对自研的意义**：这 7 个工作合起来，已经覆盖了「表示（FashionCLIP）→ 兼容性打分（Polyvore/Type-Aware/MCN）→ 诊断式反馈（MCN）→ 评测（FashionStylist）→ 召回+打分架构（Loom）」的完整链路。
> **这比逆向任何一个 App 都值钱，而且完全合法。**

## 5. 能复刻到什么程度（诚实分级）

| 层级 | 目标 | 可行性 | 法律风险 | 建议 |
|---|---|---|---|---|
| **L0** | 产品形态、交互流程、信息架构 | ✅ 完全可行 | 无（功能与思路不受著作权保护） | **直接做** |
| **L1** | 评分维度与权重 | ✅ 可行（公开信息） | 低 | **可借鉴，但必须自己校准**——别人的权重是别人的用户分布下训出来的 |
| **L2** | Prompt 文本 | ⚠️ 技术上可得 | **中**（著作权 + 可能附带他人商业植入） | **只学结构，不要整段搬**；用论文与自建规则重写 |
| **L3** | 规则库 | ❌ 基本不可得 | — | 自建（买专家知识，见 01-PRD §7） |
| **L4** | 模型权重 | ❌ 不可能 | — | 用开源底座（FashionCLIP / Qwen-VL） |
| **L5** | 用户画像数据资产 | ❌ 不可能 | — | 只能靠自己的用户积累 |

**一句话**：你能"复刻"到 **L1**，这对做 MVP 已经足够；"复刻"不到 **L3-L5**，而这恰恰是产品的长期价值。

## 6. 我的建议：不要逆向，要「逆向思维」

### 6.1 为什么逆向不值得

| 理由 | 说明 |
|---|---|
| **ROI 低** | 拿到 prompt ≠ 拿到效果。效果 = 规则库 × 评测集 × 校准。这三样逆向不来，只能自己做 |
| **风险不为零** | 违反 ToS、著作权争议、反不正当竞争；**企业级产品不能带法律瑕疵**，B 端客户会做供应商合规审查 |
| **时机不需要** | 这个品类还很年轻，公开资料（论文 + 公开 prompt + 商店文案 + 学术基线）已足够把你送到"业内第一梯队认知"。**信息差不是瓶颈，执行差才是** |
| **会抄错方向** | 抄一个把"个人辨识度"给 10% 的产品，会让你把产品做成通用审美打分器——正是你想避免的 |

### 6.2 应该做的「逆向思维」

用逆向的**思路**（拆解竞品如何做出判断），但用**合法材料**：

```
① OSINT 定口径        → 商店文案 / 公开 prompt / 定价页 / 更新日志（截图存档）
② 论文定架构          → FashionCLIP + Loom + FashionStylist + MCN
③ 专家定规则          → 搭配师把"为什么"写成 DSL（01-PRD §7）
④ 评测集定校准        → 20 套盲评，Spearman（08 号文档）
⑤ 蒸馏做冷启动        → 用公开 prompt 当 teacher，把输出蒸馏成你的规则候选（合法且高效）
⑥ A/B 定权重          → 用真实用户反馈调 D1-D5 权重
```

第 ⑤ 步是关键：**你可以合法地把公开 prompt 当作"教师模型"来生成训练/规则候选数据，而不是把它当产品代码复制。** 这是学术界标准做法，也是 ROI 最高的一步。

## 7. 如果你确实要逆向：合规操作手册

若坚持做二进制/客户端分析（如穿啥小程序），必须遵守：

| # | 规则 |
|---|---|
| 1 | 只分析**自己有权访问的公开客户端**（公开下载的 App、公开访问的网页） |
| 2 | **不绕过认证、不破解加密、不抓取需要登录的私有 API 数据** |
| 3 | 不做超出个人研究规模的大规模自动化抓取 |
| 4 | 产出物（prompt、维度、结构）**仅作内部对标参考**，不复制品牌名、UI 素材、文案 |
| 5 | **不将他人 prompt 直接用于商业产品**（改写为自建规范） |
| 6 | 上线前经法务审阅；面向公众提供生成式 AI 服务时按属地要求做备案 |
| 7 | 保留来源记录（这是"合理使用/研究"与"窃取"的分界线） |

> 越界红线：**破解、绕过鉴权、批量抓私有数据、直接搬运商业文案**。这四条任一踩中，从"研究"变成"侵权"。

## 8. 如果要做「复刻一份」的实操清单（6 步）

| 步 | 动作 | 产出 | 工时 |
|---|---|---|---|
| 1 | 采集公开情报（商店文案 / 公开 prompt / 定价 / 更新日志） | 竞品情报卡 3-5 份 | 1 天 |

## 9. 附录：实测原始记录与复现命令

```powershell
# endamai.com  → 单 script.js + styles.css ⇒ 静态营销页，无分析价值
```
