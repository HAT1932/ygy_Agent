## 1. 产品一句话

面向「每天都要决定穿什么」的高频刚需人群，输入几组参考穿搭 → 建立个人风格画像 → 对任意一套穿搭输出**可解释**的「是否适合你 + 打分 + 改进建议」报告。

**差异化不是"能打分"，而是"分数能被解释、能被追溯、能被反驳"**——每扣一分都必须指向一条具名规则和一条视觉证据。

## 2. MVP 范围

### 2.1 P0 必须做

| # | 能力 | 说明 | 验收标准 |
|---|---|---|---|
| P0-1 | 参考穿搭摄入 | 用户上传 3–5 组穿搭图（可附场景/季节文字标签） | 图片可解析出单品清单，单品识别成功率 ≥ 80%（人工抽检 20 张） |
| P0-2 | 单品结构化解析 | VLM 输出颜色/版型/材质/品类/风格标签 | 每件单品产出符合 §5 schema 的结构化对象，字段缺失率 < 10% |
| P0-3 | 风格画像构建 | 聚合为「风格标签分布 + 偏好向量 + 禁忌/偏好规则」 | 画像可展示为 top-3 风格 + 置信度，且能对同一套穿搭稳定复现（两次运行差异 < 5%） |
| P0-4 | 双塔召回 | 用户塔 × 搭配塔，向量检索 | 能对一笔画像召回 top-10 风格锚点搭配，召回结果可展示 |
| P0-5 | 待评审穿搭解析 | 同 P0-2，另加"整套搭配"结构（上/下/外套/鞋/配饰的层级关系） | 搭配结构可还原层级 |
| P0-6 | 规则引擎执行 | 首批 50 条规则（面向 1000 条的可扩展架构） | 每条命中可输出规则 ID + 触发条件 + 影响分 |
| P0-7 | Report 生成 | verdict + 总分 + 5 维度分 + 规则命中 + 建议 | 输出符合 §8 契约；100% 扣分项可追溯到规则 |
| P0-8 | 评测 | 20 套人工标注 baseline | 人机 Spearman 相关系数 ≥ 0.6 |

### 2.2 明确不做（Out of Scope，MVP 阶段）

- ❌ 商品库 / 导购 / 购买链路
- ❌ 真实虚拟试穿渲染（不生成上身图）
- ❌ 社交、UGC 社区、关注关系
- ❌ 实时摄像头识别
- ❌ 多语言（仅简体中文）
- ❌ **训练双塔模型**——MVP 用预训练嵌入 + 结构化特征拼装，不训网络
- ❌ 用户体型测量（身高体重三围）——MVP 只用图片可见信息，不要求用户填表
- ❌ 天气/日程/位置上下文

## 3. 术语表

| 术语 | 定义 |
|---|---|
| **Garment（单品）** | 一件可独立识别的衣物/鞋/包/配饰 |
| **Outfit（搭配）** | 若干 Garment 的有序集合，含层级（上装/下装/外套/鞋履/配饰） |
| **StyleProfile（风格画像）** | 单用户的可持久化风格表征，含标签分布、偏好向量、硬约束 |
| **StyleTag（风格标签）** | 受控词表标签，如「极简」「美式复古」「通勤知性」 |
| **Rule（规则）** | 一条可执行的领域知识，含条件、权重、严重度、解释模板 |
| **RuleHit（规则命中）** | 某条规则在某套搭配上的具体触发记录 |
| **Verdict（判定）** | 四档：强烈推荐 / 适合 / 一般 / 不适合 |
| **双塔（Two-Tower）** | 用户侧编码器 + 搭配侧编码器，共享同一向量空间 |

## 4. 主流程（Happy Path）

```
① 用户上传 3–5 组参考穿搭
        ↓
② 单品解析（VLM）→ Garment[]  (并行，按图)
        ↓
③ 风格画像构建 → StyleProfile{ 标签分布, 偏好向量 u, 硬约束集合 }
        ↓
④ 使用画像向量 u 召回 top-K 风格锚点搭配（双塔召回）
        ↓
⑤ 用户上传 1 套待评审穿搭
        ↓
⑥ 单品解析 + 搭配结构化 → Outfit
        ↓
⑦ 规则引擎执行 → RuleHit[]  （硬规则优先，短路可能）
        ↓
⑧ 搭配向量 v 与画像向量 u 比对 → 风格一致性特征
        ↓
⑨ LLM 评审合成（把 ⑦⑧ 的结构化结果翻译成人话建议）
        ↓
⑩ Report 输出
```

> **[B-12] 顺序修订（重要）**：原流程 ⑦→⑧ 存在数据依赖倒置——`feat.style_cosine` 是 ⑧ 的产物，却是 D2 的输入。**实际实现顺序应为：⑥ 搭配结构化 → ⑥.5 特征计算与双塔召回 → ⑦ 规则执行 → ⑧-b style_match 汇总**。03 号文档 §2 与 02 号文档时序图已按此实现。

**关键设计约束**：⑨ 的 LLM **不负责打分**，只负责**解释**。分数由 ⑦⑧ 的确定性计算得出。这是可解释性和可复现性的根，也是能过企业审计的前提。

## 5. 评分模型（决策）

### 5.1 总分

百分制，5 维度加权求和：

| 维度 | 代号 | 权重 | 考察内容 |
|---|---|---|---|
| 色彩和谐度 | D1 | **20** | 配色是否冲突、明度/饱和度关系、色不过三 |
| 风格一致性 | D2 | **25** | 与用户既有风格画像的匹配度；单品间风格是否同源 |
| 身形与比例 | D3 | **20** | 上短下长/上松下紧等比例关系、视觉重心 |
| 场合适配 | D4 | **20** | 与声明场景（通勤/约会/运动/正式等）的匹配 |
| 细节完成度 | D5 | **15** | 配饰、鞋履、层次、整洁度的收口 |

> **为什么 D2 权重最高**：本产品的价值命题是「适合**你**」，不是「这套搭配本身好不好」。通用审美打分市面上已饱和（见 06 市场调研），只有"贴合个人风格"是无法被通用模型替代的部分，所以它必须占最大权重。
>
> **为什么 D5 最低**：细节是可快速修正的，且 VLM 对细节的识别置信度最低。低权重可以在模型不确定性高的维度上降低误差放大。

### 5.2 判定（Verdict）

| 总分 | Verdict |
|---|---|
| ≥ 80 | 强烈推荐 |
| 65 – 79 | 适合 |
| 50 – 64 | 一般 |
| < 50 | 不适合 |

**硬规则一票否决**：任一 `severity = hard` 的规则触发 → Verdict 直接降为「不适合」，`total_score` 仍照算但标注 `vetoed: true` + 否决理由。

### 5.3 分数的可解释性要求（强约束）

Report 中每一分扣减必须满足：

1. 指向一条具名规则（`rule_id`）或一个具名模型特征（`feature_key`）
2. 附带该规则/特征所依据的**可见证据**（如"检测到红色上装 + 绿色下装，饱和度过高"）
3. 给出**可执行的改进建议**（不是"建议优化"，而是"把下装换成中性色如米白/藏青"）

不满足以上三点的扣分项，视为 bug。

## 6. 规则引擎契约（决策）

### 6.1 Rule Schema

```jsonc
{
  "rule_id": "R-COLOR-007",          // R-{CATEGORY}-{NNN}，全局唯一稳定
  "version": 3,                       // 规则自身版本，改动即 +1
  "category": "COLOR",                // COLOR | STYLE | PROPORTION | OCCASION | DETAIL
  "title": "高饱和撞色禁止",
  "severity": "hard",                 // hard | soft | boost
  "scope": "outfit",                  // outfit | garment | cross_garment
  "condition": {                      // 声明式 DSL，见 03 号文档
    "all": [
      { "field": "outfit.colors.hue_span", "op": "gt", "value": 120 },
      { "field": "outfit.colors.max_saturation", "op": "gt", "value": 0.85 }
    ]
  },
  "effect": { "type": "veto" },       // veto | penalty | bonus
  "score_impact": { "dimension": "D1", "delta": -8 },
  "explain_template": "上装与下装色相跨度达 {hue_span}°，且含高饱和色，视觉冲突明显。",
  "evidence_fields": ["outfit.colors.hue_span", "outfit.colors.max_saturation"],
  "source": "domain_expert",           // domain_expert | paper | reverse_engineered | learned
  "status": "active",                  // draft | active | deprecated
  "suppresses": ["R-COLOR-009"],        // [B-08] 可选：显式压制关系
  "mutex_group": "color_casual",        // [B-08] 可选：互斥组
  "suggestion_template": "把{upper.color}上装换成{alt_color_family}系",  // [B-08] 非 boost 规则必填
  "reinforce_template": "配色呼应做得到位，保持。",                       // [B-10] boost 规则必填
  "render_priority": 50,                // [B-10] 可选：同分时展示顺序
  "test_cases": []                     // 每条规则必须有至少 1 正 1 负用例
}
```

### 6.2 三类规则语义

| severity | 作用 | 是否可被其他规则抵消 |
|---|---|---|
| `hard` | 触发即 veto，套用 §5.2 | 否 |
| `soft` | 对该维度加权扣分 | 是（`boost` 可抵消） |
| `boost` | 加分（如"色彩呼应做得好"） | — |

### 6.3 执行语义

1. 按 `category` 分组，组内按 `rule_id` 排序（**确定性**，禁止依赖哈希顺序）
2. `hard` 规则全量执行（不做短路，便于一次性给出全部否决理由）
3. `soft` / `boost` 在维度内累加。**扣分上限为该维度基准分 `base_d`，加分上限为 `max_d − base_d`**（[B-01] 修订：原表述"上限为该维度权重"会破坏 §8 的"delta 之和 = 扣减"硬约束，且需额外 clamp；新表述使 `0 ≤ score_d ≤ max_d` 恒成立）
4. `boost` 只补偿同维度扣分，**受 `max_d − base_d` 预算约束，超出部分被截断并标记 `clipped: true`**（[B-09] 修订：原表述未给上限，会被实现成"无限加分"从而突破 100）
5. `base_d` 与 `base_score` 的分配方案、数值约定见 03 号文档 §2.2 / §3
6. 所有命中按确定性顺序输出，便于 diff 与回归
7. **舍入（[B-04]）**：全链路使用整数「厘点」运算（1 分 = 100 厘点），**仅在输出边界执行一次 `round_half_up`**。不写死舍入会导致 `≥ 80` 的判定在不同实现间不一致，直接违反确定性要求

### 6.4 首批 50 条规则的分层（面向 1000 条演进）

| 分类 | MVP 条数 | 目标条数 | 举例 |
|---|---|---|---|
| COLOR 色彩 | 12 | 250 | 撞色、色不过三、冷暖调性、金属色搭配 |
| STYLE 风格 | 10 | 250 | 风格同源、与画像冲突、风格混搭许可矩阵 |
| PROPORTION 比例 | 10 | 200 | 上下装长短、松紧、视觉重心、鞋型比例 |
| OCCASION 场合 | 10 | 200 | 通勤/约会/运动/正式/休闲的着装边界 |
| DETAIL 细节 | 8 | 100 | 配饰数量、层次、材质呼应、季节一致性 |

> MVP 只做 50 条，但 **schema、版本、测试用例、DSL 必须按 1000 条设计**——规则资产的工程化程度才是护城河，不是规则数量。

## 7. 双塔召回（决策）

### 7.1 结构

```
        用户侧                          搭配侧
  StyleProfile(标签+偏好)          Outfit(单品属性+图像)
         ↓                                 ↓
   ┌─────────────┐                  ┌─────────────┐
   │ User Tower  │                  │ Outfit Tower│
   └─────────────┘                  └─────────────┘
         ↓                                 ↓
   u ∈ R^256                          v ∈ R^256
         └──────── cosine(u,v) ────────────┘
```

### 7.2 MVP 实现方式（不训练）

| 部分 | 来源 |
|---|---|
| 图像特征 | 跨模态嵌入模型（CLIP/SigLIP 系或中文 CLIP），L2 归一化后取 128–256 维 |
| 结构化特征 | StyleTag 多热向量 + 颜色/版型/材质 one-hot，经固定投影降维 |
| 拼接 | `concat(α·img_emb, β·struct_proj)`，α+β 归一化；α、β 为可调超参（初值 0.6/0.4）。**[B-11] 注意：由于 cosine 按平方生效，α=0.6/β=0.4 的真实权重是图像 69.2% / 结构 30.8%，不是 60/40；且 `img_dim`、`struct_dim` 必须钉死，否则不同实现的向量不可比** |
| 用户塔 | 其参考穿搭 outfit 向量的**加权平均**（权重 = outfit 完整度） |
| 搭配塔 | 该 outfit 的 img_emb + struct 特征 |

**为什么可以不训练**：MVP 只需要"相似度可用"而非"最优"。预训练跨模态嵌入已具备风格语义（taste embedding），足以支撑演示与人工相关性验证。留出训练接口（`TowerAdapter`）即可，二期用用户反馈对做对比学习。

### 7.3 召回的三处用途（这是双塔在本产品里的真实价值）

1. **风格锚点**：从搭配库里召回与用户画像最像的 top-K，作为报告里的"参照系"（"这套和你常穿的 X 风格相近"）
2. **候选生成**：画像 → 召回 → 作为"你可以尝试的方向"推荐
3. **一致性特征**：`cosine(u, v)` 直接作为 D2 的一个输入特征

> 注意：双塔在本产品**不是用来做商品召回的**（我们没有商品库）。它的作用是建立"个人风格的度量空间"。这一点写进文档是为了防止团队按电商推荐系统的惯性做错方向。

## 8. Report 数据契约（决策草案）

```jsonc
{
  "report_id": "rpt_01HXY...",
  "outfit_id": "oft_01HXY...",
  "profile_id": "prf_01HXY...",
  "created_at": "2026-10-31T12:00:00+08:00",

  "verdict": "suitable",              // strongly_recommended | suitable | neutral | unsuitable
  "vetoed": false,
  "total_score": 72.5,                // 0-100，保留 1 位小数
  "base_score": 70.0,                 // [B-02] 必填：本文档 §6.3 的基准分常量（随 ruleset 冻结）。不写它，"扣减可解释"无法脚本校验
  "confidence": 0.78,                 // 0-1，模型/解析置信度

  // [B-02] 另需补齐（完整 Schema 以 04 号文档为准）：
  //   dimension_scores[].base            每维度基准分 base_d
  //   dimension_scores[].assessability   0-1，该维度证据可用度（决定门控）
  //   dimension_scores[].penalty_used / boost_used   实际消耗的预算
  //   score_ledger[]                     逐笔生效值 + clipped 标记（审计与回归用）

  "dimension_scores": [
    { "code": "D1", "name": "色彩和谐度", "score": 16.0, "max": 20, "weight": 0.20 },
    { "code": "D2", "name": "风格一致性", "score": 18.5, "max": 25, "weight": 0.25 },
    { "code": "D3", "name": "身形与比例", "score": 15.0, "max": 20, "weight": 0.20 },
    { "code": "D4", "name": "场合适配",   "score": 15.0, "max": 20, "weight": 0.20 },
    { "code": "D5", "name": "细节完成度", "score": 13.0, "max": 15, "weight": 0.15 }
  ],

  "rule_hits": [
    {
      "rule_id": "R-COLOR-003",
      "title": "色不过三",
      "severity": "soft",
      "dimension": "D1",
      "delta": -4,
      "triggered_value": 4,
      "evidence": "本套含黑/白/红/军绿 共 4 个主色",
      "explanation": "主色超过 3 个，视觉信息过载。"
    }
  ],

  "style_match": {
    "user_top_styles": ["极简", "通勤知性", "法式"],
    "outfit_styles": ["极简", "运动休闲"],
    "cosine": 0.81,
    "matched": ["极简"],
    "drifted": ["通勤知性 → 运动休闲"]
  },

  "anchors": [
    { "outfit_id": "oft_...", "similarity": 0.91, "thumb_url": "..." }
  ],

  "suggestions": [
    {
      "priority": 1,
      "target": "下装",
      "action": "把军绿工装裤换成藏青锥形西裤",
      "reason_rule_ids": ["R-STYLE-004", "R-COLOR-003"],
      "expected_gain": 6.5
    }
  ],

  "summary": "……一句话总评（由 LLM 基于以上结构化结果生成，不得引入新事实）……",

  "meta": {
    "model_versions": { "vlm": "...", "llm": "...", "embedding": "..." },
    "ruleset_version": "rs-2026.10.1",
    "parse_warnings": []
  }
}
```

**硬约束**：
- `rule_hits` 的 `delta` 之和必须等于 `total_score` 的扣减可解释部分；差额只能来自 `base_score`（默认给予的基准分，需显式写出）
- `summary` 由 LLM 生成，但**禁止**出现 `rule_hits` 之外的新判断（需做事实一致性校验）
- `suggestions.expected_gain` 需可与 `dimension_scores` 对齐

> `base_score` 字段待 03 号文档定稿时补齐——见风险 R-04。

## 10. 评测与质量门槛

| 指标 | 门槛 | 测法 |
|---|---|---|
| 人机总分 Spearman | ≥ 0.6 | 20 套人工标注（3 名标注者取均值） |
| Verdict 4 分类准确率 | ≥ 65% | 同上 |
| 扣分可追溯率 | **100%** | 脚本校验每个扣分项有 rule_id |
| 规则回归通过率 | 100% | 每条规则的正负用例 |
| 单品识别成功率 | ≥ 80% | 人工抽检 20 张图 |
| 端到端 P95 延迟 | ≤ 20s | **单次 report 生成**（含解析 + 规则 + LLM 合成），**不含图片上传与画像首次构建**（[B-07] 修订：上传耗时受网络影响不可控，混计会让门槛永远达不成） |

## 11. 关键风险与降级方案

| ID | 风险 | 影响 | 降级方案 |
|---|---|---|---|
| R-01 | VLM 颜色/材质识别不准，导致规则误触发 | 高 | 颜色用色卡聚类回退；材质识别不确定时该规则降级为 `soft` 或跳过并记 `parse_warnings` |
| R-02 | 规则爆炸后互相冲突（1000 条时） | 高 | 规则分组互斥 + 单维度扣分上限 + 冲突检测离线任务 |
| R-03 | LLM 解释"编造"结论 | 高 | 结构化输入 → 模板化生成；LLM 只做润色，事实校验拦截 |
| R-04 | `base_score` 定义不清导致分数不可复现 | 中 | 03 号文档必须给出确定性基准分算法 |

| R-06 | 隐私：用户上传真人穿搭照片 | 高 | 只提取结构化特征，原图短期存储 + 可删除；文档需写明 |

## 12. 评审回填：来自派生文档的修订（v0.2）

实现文档（02/03/04）在落地过程中发现本节 v0.1 的若干表述会**破坏自身的硬约束**。以下条目已回填；完整论证与数据在对应文档中。**发生冲突时，以本节已回填的表述为准。**

| ID | 原表述的问题 | 回填结果 | 状态 |
|---|---|---|---|
| **B-01** | §6.3「扣分上限=维度权重」会导致 delta 求和 ≠ 扣减，需额外 clamp | 改为上限 = `base_d`，加分上限 = `max_d − base_d` | ✅ 已回填 §6.3 |
| **B-02** | §8 声称"差额只能来自 base_score"，但契约里没有该字段 | 新增 `base_score`、`base`、`assessability`、`penalty_used`/`boost_used`、`score_ledger` | ✅ 已回填 §8 |
| **B-03** | §11 R-05「降低 D2 权重」会破坏固定权重与 `weight` 之和 = 1.00 | 改为缩放特征增量 `feat.style_cosine`，权重不动 | ✅ 已回填 §11 |
| **B-04** | 未规定舍入 → `≥80` 判定会因实现而异 | 全链路厘点整数运算，输出边界 `round_half_up` 一次 | ✅ 已回填 §6.3-7 |
| **B-05 / B-18** | §9 仅 6 个端点，不足以支撑已承诺的异步语义与隐私要求 | 补 9 个端点（任务查询、报告列表、反馈、重放、规则集、直传、删除、清除） | ✅ 已回填 §9 |
| **B-07** | §10「P95 ≤ 20s」未限定范围，含上传则永不可达 | 限定为「单次 report 生成」，不含上传与首次画像 | ✅ 已回填 §10 |
| **B-08 / B-10** | §6.1 schema 缺承载冲突消解与"改法"的字段 | 新增 `suppresses`/`mutex_group`/`suggestion_template`/`reinforce_template`/`render_priority` | ✅ 已回填 §6.1 |
| **B-09** | §6.2 只说 boost「加分」，未给上限 | 明确受 `max_d − base_d` 预算约束，超出截断并标 `clipped` | ✅ 已回填 §6.3-4 |
| **B-11** | §7.2 的 α=0.6/β=0.4 被误读为 60/40 | 明确真实权重为 **69.2% / 30.8%**（cosine 按平方生效），且 `img_dim`/`struct_dim` 须钉死 | ✅ 已回填 §7.2 |
| **B-12** | §4 的 ⑦→⑧ 数据依赖倒置 | 改为 ⑥ → ⑥.5 特征/召回 → ⑦ 规则 → ⑧-b style_match | ✅ 已回填 §4 |
| **B-06** | §7.2「固定投影」未指定确定性来源 | 要求固定种子矩阵或 feature hashing + 固定 salt，投影矩阵 `sha256` 随 ruleset 发布 | ⏳ 由 02/04 号文档约束 |
| **B-26** | `rule_id` 分类段实际用短码（PROP/OCC/DET），与 v0.1 的全称正则不一致 | 采用 `CATEGORY_SHORT` 映射表，并以 validator 断言固化 | ⏳ 由 03/04 号文档约束 |

> **仍未闭环的一条**：03 号文档发现 boost 加分总量（38 分）> 加分容量（30 分），导致"优秀搭配必然触发截断"（算例 C 丢弃 6.38 分）。缓解方案是 `base_score` 70→62 并同步扩容，但那是**破坏性变更**（需重跑标注集校准）。**列为 M5 评测阶段的决策项**，不在 v0.2 强制执行。
