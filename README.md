> 面向「每天都要决定穿什么」的高频刚需人群，用 **多模态大模型 + 千条规则引擎** 做「千人千面、可解释」的穿搭评审。

## 一、三个问题的直接答案

### Q1「这个最小可行 demo 怎么实现？」

**一句话**：把它拆成一条**确定性流水线**，模型只负责"看懂图"和"说人话"，**打分绝不由模型决定**。

```
参考穿搭图 ──VLM──> 单品结构化 ──> 风格画像(标签分布+偏好向量)
                                          │
新穿搭图 ──VLM──> 搭配结构化 ──> 规则引擎(50条) ──> 维度分(D1-D5) ──> 总分+等级
                                          │                              │
                                   双塔相似度 ────────────────> LLM 只做"解释"
                                                                         │
                                                                    Report
```

**四个关键技术决策**（理由见 [00-baseline](./docs/00-baseline.md)）：

| 决策 | 取值 | 为什么 |
|---|---|---|
| 评分维度与权重 | 色彩 20 / **风格一致性 25** / 比例 20 / 场合 20 / 细节 15 | 价值命题是"适不适合**你**"，个人匹配必须占最大权重 |
| 规则引擎 | MVP 只上 **50 条**，但 schema/版本/测试/DSL 按 **1000 条** 设计 | 护城河是规则的**工程化程度**，不是数量 |
| 双塔召回 | **256 维，不训练**，用预训练跨模态嵌入 + 结构化特征拼装 | 没有用户反馈数据时训练是伪需求；先靠预训练嵌入拿到可用的"风格度量空间" |
| LLM 的职责 | **只解释、不打分** | 分数必须确定性可复现、可审计。这是能过企业审查的前提 |

### Q2「市面上有哪些产品贴合度较高？」

**分三层，结论是"红海 + 空白"并存：**

| 分层 | 代表 | 与我们重合度 | 关键事实 |
|---|---|---|---|
| **穿搭评审/打分**（最贴近） | 穿搭日记、Endam、DRESSED、Judge My Outfit、Roast My Style、Modebase、穿啥 | **极高** | 全是「一张照片 → 一个分数 + 几条建议」。**40 个同类 App 绝大多数评分人数 0–16，中国区 0–4** |
| 数字衣橱 | Whering、Acloset、Cladwell、Style DNA、今穿 | 中高 | **有量**：尽简衣橱 23,729 评分。但没有做"评审" |
| AI 试穿 | Google Doppl（**已关停**）、ASOS、Zalando、Meta Style Sketch | 中 | 解决"像不像我"，不解决"适不适合场合" |
| B2B 基础设施 | Lily AI、Syte、Pixyle、ViSenze | 低 | **无人卖「穿搭是否成立、为什么」** |

**三条最有价值的调研结论**：

1. **「能打分」零差异化**——这个品类已被几十个团队试过且全部失败（见上表数字）。
2. **用户愿为"管理衣橱"付费，不愿为"给我打分"来**——所以若"画像"不可感知/可回看/可分享，用户不会为打分留存。
3. **「先学你的风格 → 再评审新搭配 → 且可解释」这件事，未发现有人做**。最近的三个各差一步：Style DNA 画像是自拍生物特征且只判单品；Cladwell 会学风格但只生成不评审；小衣橱会点评但没有学习型画像。
   > 注意：**这是"难而正确"，不是"容易没人做"**。竞品集体绕开"上传画像"是因为零输入通用打分最好上线。

详见 [06-market-scan](./docs/06-market-scan.md)（含完整证据台账与未查证清单）。

### Q3「我能否通过 REA 逆向复刻一份？」

**能复刻到 L1，复刻不到 L3；而且我实测后发现——不值得逆向。**

| 层级 | 目标 | 能否复刻 |
|---|---|---|
| L0 | 产品形态、交互、信息架构 | ✅ 可以（功能不受著作权保护） |
| L1 | 评分维度与权重 | ✅ 可以，且**本轮已拿到** |
| L2 | Prompt 文本 | ⚠️ 可得，但只学结构、不要整段搬 |
| L3 | **规则库 / 专业判断知识** | ❌ 逆向不到 |
| L4/L5 | 模型权重 / 用户画像数据 | ❌ 不可能 |

**本轮实测（真实动手，不是推演）**：
- 已跑通 Chrome 156 + CDP + 静态 bundle 分析链路（捕获 6 脚本、1396 AST 节点、0 解析失败）
- 对 DRESSED（纯 Web）实测：全部 JS 仅 **11.6KB**，无路由、无 API 端点 —— **它是个营销页，应用逻辑在服务端**
- 结论：**这个品类的护城河在服务端，逆向客户端拿不到评分逻辑**

**本轮用合法手段拿到的、比逆向更值钱的东西**：
- **Modebase 公开的完整专家级 styling prompt**（含"不许默认夸我"的反谄媚约束、身形读法、上/下半身规则、缺件必须声明 Missing 的反幻觉机制）
- **穿搭日记的评分权重**：整体协调 3 / 时尚 2 / 场景 2 / 细节 2 / **个人辨识度 1**（10 分制）→ **竞品把"个人化"压到 10%，我们把"风格一致性"提到 25%，这是定位差异的量化证据**
- **7 个可直接复现的学术基线**：FashionCLIP（嵌入底座）、OutfitTransformer、MCN（诊断式反馈）、FashionStylist（评测口径）、Loom（检索+打分架构）、Polyvore / Type-Aware Embeddings

**建议**：不要逆向，要「逆向思维」——OSINT 定口径 → 论文定架构 → 专家定规则 → 评测集定校准。合规红线与操作手册见 [07-rea-feasibility](./docs/07-rea-feasibility.md) §7。

## 二、技术选型（含真实抓取的价格）

**推荐组合**（完整论证见 [05-tech-stack](./docs/05-tech-stack-and-model-selection.md)）：

| 层 | 推荐 | 理由 |
|---|---|---|
| VLM（图片解析） | **阿里云百炼 Qwen3.7-Plus** | 国内直连、中文服饰术语稳、**唯一可把图像细节从 1,024 加到 16,384 token**、同族 8B/32B 有开源退路 |
| 文本 LLM（只解释） | **DeepSeek `deepseek-flash`** | 最低档（输入 1 元 / 输出 4 元 每百万 token），中文表达正好满足唯一硬需求 |
| Embedding（双塔） | **qwen3-vl-embedding** | MVP 月调用仅千级，不值得自建 GPU |
| 向量库 | **PostgreSQL + pgvector** | 一年 < 5 万向量，省一个组件，删用户一条 SQL |
| 后端 / 队列 | **FastAPI + Pydantic v2 / Celery + Redis** | 契约为王；`202 + task_id` 异步协议 |
| 对象存储 | **阿里云 OSS**（与百炼同区） | 内网传图免流量费，生命周期自动删除 |

**三档月成本**（真实单价抓取于 2026-10-31，用量 = 1,000 次报告 + 100 用户建画像/月）：

| 档 | 组合 | 月成本 | 单份报告 |
|---|---|---|---|
| A 极致省钱 | DeepSeek 全包 | **≈ 17.30 元** | ≈ 1.37 分 |
| **B 推荐** | Qwen3.7-Plus 解析 + DeepSeek 合成 | **≈ 25.21 元** | ≈ 1.94 分 |
| C 质量优先 | Qwen3.8-Max 全包 | ≈ 153.58 元 | ≈ 12.38 分 |

> **A → B 只差 7.91 元/月**。用 8 块钱买「2.5 倍视觉细节 + 开源退路」是明显正确的交易。
> 外推到 10 万次/月 ≈ 2,521 元 → **成本在很长时间内都不是这个产品的竞争约束**，选型不该由"省模型钱"驱动。

⚠️ **两个必须知道的技术坑**：
1. 百炼 `qwen3.7/3.8` 系列**默认开启 thinking**，不显式关闭会让成本 **+67%**
2. 所有成本建立在「每图 1,024 image token」这个**官方公式**上，**上线前必须用 30 张真实图回读 API `usage` 校准**（可能有 ±10% 偏差）

## 三、三个必须正视的风险

| # | 风险 | 依据 | 应对 |
|---|---|---|---|
| **R-01** | **"能打分"没有差异化，这条路上已横着几十个失败产品** | 40 个同类 App 评分人数 0–16（[06](./docs/06-market-scan.md) §2.3） | 差异化必须落在「个人画像 + 可解释 + 可审计」，不能落在"AI 打分" |
| **R-02** | **H1（用户愿意上传 3–5 组参考穿搭）是整个品类从未验证过的假设** | 竞品集体绕开这一步 | **"先给示例报告、后建画像"的 A/B 必须提前到 M1**，不能等 M4 |
| **R-03** | **"正确的废话"**——LLM 生成的建议听起来对但无法执行 | LLM 天然倾向讨好 | 强制"把 X 换成 Y"格式；扣分 100% 可追溯到规则；每条规则必须自带"改法" |

## 五、这套设计的三个"不妥协"

1. **分数必须确定性**：同一（画像, 搭配, 规则版本）→ 永远同一分、同一顺序。否则无法审计、无法回归、无法 A/B。
2. **扣分必须可追溯**：每个扣分项都要能指到 `rule_id` + 视觉证据 + 具体改法。做不到就是 bug。
3. **模型不得越权**：LLM 只做"翻译成人话"。它一旦参与打分，可解释性和可复现性同时崩塌。

## 六、下一步（若进入实现）

| 优先级 | 动作 | 为什么要先做它 |
|---|---|---|
| 1 | **规则引擎 + fixture 测试**（不接模型） | 判断力的地基；且确定性可测 |

| 3 | **Report 组装**（结构化 → 契约 JSON） | 交付物本体 |
| 4 | VLM 适配器 | 把数据喂进已测好的引擎 |

> 关键顺序判断：**先做确定性的部分，VLM 只是往里喂数据**。反过来会陷入"模型输出不稳定 → 无法判断规则对不对"的死循环。
