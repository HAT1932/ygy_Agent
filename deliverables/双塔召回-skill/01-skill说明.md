# 11 · Skill：穿搭适配评审（Twin-Tower Outfit Review）

> 交付物：一个**可复用的判断能力**，不是一次性的聊天记录。
> 输入「用户的 3–5 套参考穿搭 + 1 件待评穿搭」，输出「适不适合 / 分数 / 原因 / 风险 / 建议」。
> 换一件衣服只需重跑判断层，画像不用重建。
>
> 本文所有数字均来自本仓库实测（`eval/report.json`、`docs/10-implementation-findings.md`），
> 未实测的地方会明确标注「未验证」。

---

## 1. Skill 概述

| 项 | 内容 |
|---|---|
| **skill 名称** | `outfit-fit-review`（穿搭适配评审） |
| **一句话定义** | 给一个用户的风格画像和一件衣服，判断这件衣服适不适合他，并给出**可追溯的分数、原因、风险与改法**。 |
| **解决什么问题** | 把「我今天穿这样行不行」从主观闲聊，变成**可复现、可解释、可批量**的结构化判断：同样输入永远同样结论；每条扣分都有出处；一次搭好画像，之后每件衣服都能秒判。 |
| **不解决什么** | 不做单品推荐/购物搜索，不做身材测量，不做虚拟试衣。 |

### 和「双塔召回」的对应关系

| 层 | 在本 skill 里是什么 | 具体产物 | 谁来做 |
|---|---|---|---|
| **用户塔** | 把 3–5 套参考穿搭压成一个**风格画像** | `StyleProfile`：受控风格标签分布(带权重) + 风格家族 + 习惯正式度 + 禁用/想尝试 + 画像向量 | 规则聚合为主，LLM 只做命名与总结 |
| **衣服塔** | 把一件（套）衣服解析成**结构化单品** | `Outfit`：6 类 slot 单品，每件含 hex/hue/明度/正式度/风格词/图案/商家标题 | 视觉模型（VLM）+ 确定性归一化 |
| **判断 / 重排层** | 画像 × 单品 → 分数与结论 | 50 条规则命中 → 五维预算打分 → `verdict` + `rule_hits` + `suggestions` | **纯规则引擎**（LLM 不参与判断） |

**和教科书双塔的差异（要主动说出来，这是加分点）**：
标准双塔是「用户向量 × 候选库向量 → cosine top-K」的**召回**。面试任务是**单件判断**，
所以本 skill 把「召回」降级为可选：画像向量只用来算一个 `style_cosine` 作为规则输入，
真正的排序由规则引擎完成。理由很实际——cosine 只能回答"像不像"，回答不了
"这套在通勤场合正式度够不够、裤长会不会堆在鞋面"。**召回负责缩小范围，规则负责下结论。**

## 2. Skill 输入契约

### 2.1 用户塔输入

| 字段 | 类型 | 必填 | 约束 / 说明 |
|---|---|---|---|
| `profile_id` | string | ✅ | 画像唯一 ID |
| `refs[]` | array | ✅ | 参考穿搭，**建议 3–5 套**；硬上限 10（超过直接拒绝，不静默截断） |
| `refs[].image_ref` | string | ✅ | 本地路径 / http(s) / data URI；引号、`file://`、空白都要先归一化 |
| `banned_styles[]` | string[] | ⭕ | 用户声明「绝对不穿」。**强烈建议必填**：不填，个性化区分度只有 5.0 分（门槛 8 分）；填了到 8.0 分 |
| `explore_tags[]` | string[] | ⭕ | 用户想尝试的风格，用于"探索加分" |
| `note` | string | ⭕ | 自由备注，只进提示词，不参与打分 |

### 2.2 衣服塔输入（单品结构，每件）

| 字段 | 类型 | 取值 | 说明 |
|---|---|---|---|
| `slot` | enum | `upper` / `lower` / `outer` / `dress` / `shoes` / `accessory` | 决定单品权重（dress=1.0，shoes=0.6，accessory=0.45） |
| `category` | string | 中文品类 | 用于正式度夹逼（卫衣→≤2，西装→≥4） |
| `colors[]` | object[] | `{hex, name}` | **必须给真实 hex**；hue/saturation/lightness 由 hex 确定性推导，不让模型猜 |
| `formality` | enum / int | `loungewear\|casual\|smart_casual\|business\|formal` → 1–5 | **用词不用裸数字**：数字没有方向，实测模型会把卫衣标成 5 |
| `style_tags[]` | string[] | 受控 25 词表，每件 ≤2 | 见 §2.3 |
| `style_words[]` | string[] | 自由词，≤4 | 低腰/露脐/厚底/波点/豹纹/千禧感…词表覆盖不了的细节都放这里 |
| `pattern` | enum | `solid\|stripe\|check\|floral\|graphic` | 闭集 5 值，避免"波点"被塞进 graphic |
| `pattern_detail` | string | 波点/豹纹/千鸟格 | 只做证据，不进向量 |
| `merchant_title` | string | ≤20 字 | 让模型按商家口吻写（"Y2K辣妹 波点连帽卫衣 宽松"）：**风格词富矿，零成本复刻商品标签** |
| `confidence` | float | 0–1 | <0.6 视为证据不足，进诊断 |
| `evidence` | string | 一句话 | 视觉证据原文，出问题时可回溯 |

## 3. Skill 输出契约

| 字段 | 说明 |
|---|---|
| `verdict` | `strongly_recommended` / `suitable` / `neutral` / `unsuitable` → 中文：强烈推荐 / 适合 / 一般 / 不适合 |
| `total_centi` | 总分，**整数厘点**（7000 = 70.00 分），不用浮点，避免边界抖动 |
| `vetoed` | 是否触发一票否决（硬规则）。`vetoed=true` 时 `verdict` 必为「不适合」 |
| `dimensions[]` | 五维得分：D1 色彩 20 / D2 风格 25 / D3 比例 20 / D4 场合 20 / D5 细节 15（满分合计 100） |
| `rule_hits[]` | 每条：`rule_id` + `title` + `severity` + `delta_schema`（规则声明扣分）+ `delta_applied`（预算截断后实际生效）+ `evidence`（证据原文）+ `suggestion`（改法） |
| `suggestions[]` | 按 `expected_gain` 降序，最多 3 条，格式为「把 X 换成 Y」级可执行，且 `expected_gain` 必须能对上账本 |
| `risks[]` | **风险 ≠ 原因**：原因是"哪里不对"，风险是"不改会怎样"。每条含 `rule_id` + `risk`（后果）+ `suggestion` + `expected_gain` |
| `score_ledger[]` | 逐条记账：序号 / 规则 / 维度 / 声明分 / 生效分 / 是否被预算截断 |
| `diagnostics[]` | 人可读诊断：`code` / `severity(info\|warn\|error)` / `label` / `detail` / `impact` / `refs`（第几张图） |
| `meta.data_source` | `vlm` 或 `mock`。**只要解析没看真图就必须标 mock**，这是一票否决级的诚实字段 |

### 三条不变量（自测时每条都要断言）

1. **可加性**：`total_centi == base_centi + Σ delta_applied_centi`（整数，无浮点误差）
2. **可追溯**：每条扣分必须有 `rule_id` + `evidence`；扣分项必须有 `suggestion`
3. **预算守恒**：每个维度 `base_d + boost_budget_d == max_d`；扣分不得把维度打穿到负数

## 4. 判断规则清单

### 4.1 打分口径（先定口径，再写规则）

| 维度 | 名称 | 满分 | 基准 base_d | 加分预算 | 权重 |
|---|---|---|---|---|---|
| D1 | 色彩和谐度 | 20 | 15.6 | 4.4 | 0.20 |
| D2 | 风格一致性 | 25 | 18.0 | 7.0 | 0.25 |
| D3 | 身形与比例 | 20 | 13.2 | 6.8 | 0.20 |
| D4 | 场合适配 | 20 | 13.6 | 6.4 | 0.20 |
| D5 | 细节完成度 | 15 | 9.6 | 5.4 | 0.15 |
| — | **合计** | **100** | **70.0** | **30.0** | 1.00 |

判定阈值：`≥80 强烈推荐` / `65–79.9 适合` / `50–64.9 一般` / `<50 不适合`；**任何硬规则命中 → 直接不适合**。

> 为什么基准是 70 而不是 0：0 基准意味着"默认你有罪"，一条规则没命中就 100 分，
> 系统会失去分辨力。70 起、扣到 0、加到 100，且每维度加分有预算，
> 保证"没有短板的搭配自然 75–80"，不需要调参数凑分。

### 4.3 写规则的 6 条硬约定

1. **hard 规则必须一票否决**，且只有 hard 能否决；boost 必须正分且必须写"加分说明"。
2. **每条扣分必须给建议**，且建议不得假设具体单品（不能写"把西装外套换成…"），
   也不许用"那件/它"这类指代——否则换一套衣服就读不通。
3. **规则不得知道 embedding 实现**：余弦阈值必须按后端标定/归一化后再喂规则，否则换模型全线失灵。
4. **色相统计只算有彩色**（saturation ≥0.15）：黑白灰没有色相，把黑算成 0° 会造出假撞色。
5. **主色先聚类再计数**：近似色算一个，否则"黑鞋+黑裤+黑包"会被算成三个颜色。
6. **改规则必须同时有正例与负例**：34% 的规则曾在真实解析能力下完全没有区分度（恒命中/恒不命中），
   这类"静默失效"比崩溃更危险。

## 5. Skill 工作流

| # | 步骤 | 做什么 | 谁来做 | 失败时 |
|---|---|---|---|---|
| S1 | **输入预检** | 路径归一化（去引号/`file://`/空白）、张数校验、可解码性预检 | 规则 | 明确报错并停下，**绝不降级造数据** |
| S2 | **衣服塔解析** | 主体裁剪 → VLM 输出结构化单品 JSON | **大模型**（视觉） | 重试 1 次 → 仍失败则标 `data_source=mock` 并红条提示 |
| S3 | **归一化** | 正式度词→1–5、fit/length/pattern 别名→闭集、风格词展开成家族 | 规则（确定性） | 无法映射的字段置空 + 记诊断，不臆测 |
| S4 | **用户塔聚合** | 标签加权分布（slot 权重 × 置信度）、家族分布、习惯正式度、画像向量 | **规则为主**（LLM 只做命名与总结） | 参考 <3 套则 `confidence <0.6` 并提示补图 |
| S5 | **证据门控** | 每维算 `assessability`（0–1）；<0.5 该维度**跳过规则、保留基准分** | 规则 | 缺鞋/缺色/遮挡 → 降权 + 诊断说明影响 |
| S6 | **规则命中 + 打分** | 逐条求值 → 预算截断 → 五维分 → 总分 → 判定 → 记账 | **规则引擎** | 断言不变量，违反即报错 |
| S7 | **文案生成** | 模板先拼出事实摘要 → 可选 LLM 润色 → 事实校验（数字/评价词/术语） | 模板 + LLM（只润色） | 校验不过 → 回退模板 |
| S8 | **人工确认** | 用户看"结论 + 3 条原因 + 3 条风险 + 3 条建议"，可标记"这条不对" | **人** | 标记回流成 badcase，进 §8 归因表 |

### 哪些必须交给规则引擎，哪些可以交给大模型

| 环节 | 归谁 | 理由 |
|---|---|---|
| 单品识别（它是什么、什么颜色、什么图案） | 大模型 | 只有它能看图；但输出必须落成闭集字段 |
| 风格命名（这套像什么风） | 大模型候选 + 受控词表归一 | 让它自由输出，一定会出现词表外词汇被丢弃（§11.1） |
| 分数与判定 | **规则引擎** | 要可复现、可追溯、可回归测试；LLM 每次给的分数都不一样，无法验收 |
| 原因与建议的措辞 | 模板 → LLM 润色 | 判断不能由 LLM 新增，只能改写既有事实 |
| 禁用风格、场合声明 | **人** | 这是用户主观意愿，模型无权替他决定 |

**一句话原则**：**模型负责"看见"，规则负责"判断"，人负责"愿不愿意"。**

## 6. Prompt 模板

三个 prompt 各管一件事，**不要合并**。公共参数：`temperature=0`、
`response_format={"type":"json_object"}`、`enable_thinking=false`（百炼 qwen3.x 默认开思考，不关会贵 67% 且更慢）。

### 6.1 用户塔：画像聚合

```
system:
你是用户风格画像聚合器。输入是同一用户 3-5 套参考穿搭的结构化解析结果。
只输出一个 JSON 对象，不要解释、不要 Markdown：
{
  "tags": [{"tag": "受控词表里的风格", "weight": 0到1的小数}],
  "family_tags": ["风格家族名"],
  "preferred_formality": 1到5的整数,
  "banned_styles": [], "explore_tags": [],
  "signature_colors": ["最多3个主色名"],
  "silhouette_habits": ["最多2条版型习惯，如 上短下长 / 宽松为主"],
  "confidence": 0到1的小数
}
规则：
1. tags 必须从给定受控词表里选，最多 5 个，weight 归一化后和为 1，按权重降序。
2. 参考数量 <3 时 confidence 必须 <0.6。
3. 只在证据里出现过的风格才能写；拿不准就不写，不要凑数。
4. family_tags 用来表达受控词表覆盖不到的说法（Y2K/千禧/古早 都归「千禧辣妹」）。

user:
受控词表：极简 / 通勤知性 / 法式 / 甜美 / 运动休闲 / 街头潮流 / 商务正装 / …
参考穿搭：[ {outfit_id, occasion, items:[{slot, category, colors, formality, style_tags, style_words, merchant_title}]} ]
```

> 关键设计：**输入是结构化的解析结果，不是图片**。理由：① 5 张图重看一遍要多付 5 次
> VLM 调用（≈11s/张）；② 让模型对着已结构化的字段做聚合，比让它"再看一遍图总结风格"稳定。

### 6.2 衣服塔：单品解析（VLM）

```
system:
你是服装搭配解析器。只输出一个 JSON 对象，不要解释、不要 Markdown。
{"items":[{"slot":"upper|lower|outer|dress|shoes|accessory","category":"中文品类",
"color":{"name":"中文色名","hex":"#RRGGBB"},"material":"棉/羊毛/真丝/牛仔/牛皮/针织",
"fit":"tight|slim|regular|loose|oversized","length":"crop|short|regular|long|maxi",
"formality":"loungewear|casual|smart_casual|business|formal","style_tags":["受控词表1-2个"],
"style_words":["细粒度线索：低腰/露脐/厚底/波点/豹纹/金属配件"],
"pattern":"solid|stripe|check|floral|graphic","pattern_detail":"波点/豹纹/千鸟格，纯色留空",
"merchant_title":"<=20字商家口吻标题","confidence":0到1,"evidence":"一句视觉证据"}]}

规则：
1. 看不见的字段给 null，不要编造；颜色必须给真实 hex，不确定则 confidence<0.6。
2. style_tags 每件最多 2 个，只给主导风格；不要把整套写成同一个词，也不要每件都不同。
3. formality 用英文词，不要给数字（1=家居, 3=半正式, 5=礼服）。
4. 波点/豹纹/拼接写进 pattern_detail 与 style_words，pattern 只填 5 个闭集值。
5. 低腰 + 露脐/短款 + 厚底 + 波点/豹纹 + 金属配件，通常属 Y2K/千禧/古早 谱系：
   受控词写 甜酷 或 街头潮流，把 千禧感/古早感/波点 写进 style_words。
6. 不要漏单品：下缘只露鞋头也要输出 shoes；明显的包/袜/腰带各列一条 accessory；总数 ≤6。
7. 判定主导风格先看廓形与配件组合，再看颜色与气质。

user:
请解析这套穿搭中的全部单品。用户声明的场合：{occasion}；季节：{season}。
```

> 为什么规则 5 要写死"Y2K 对应甜酷/街头潮流"：不写，模型会把同一套判成"日系少女/学院风"，
> 而我们词表里没有这些词，信号会整段丢掉（§11.1）。

### 6.3 判断层：文案润色（可选）

```
system:
你是中文穿搭报告文案润色器，只能改写给定事实，禁止新增任何事实。
1. 不得新增数字：文本中每个数字都必须与输入 JSON 一致。
2. 不得新增评价：禁止「高级感/显瘦/气质/百搭/上档次/质感/利落/完美/惊艳/绝了/氛围感」。
3. 判定词只能使用输入中的 verdict_cn，不得写成其他等级。
4. 不得出现规则编号、维度代号（D1）、"规则""delta""维度"等内部术语。
5. 只能改写总结句，不得新增建议。
6. 不超过原摘要 1.5 倍，中文 1–3 句，以「。」结尾。
只输出 JSON：{"summary": "..."}

user:
{"verdict_cn":"适合","total_score":74.0,
 "dimensions":[{"name":"风格一致性","score":21.0,"max":25.0}],
 "issues":[{"title":"图案叠加撞色","evidence":"薄荷绿与棕同时高饱和"}],
 "suggestions":[{"target":"托特包","action":"换成黑色或米白","expected_gain":2.0}],
 "改写基线":"这套搭配得 74 分，判定为「适合」…"}
```

**润色后必须过机检**（否则回退模板）：数字白名单校验 + 主观词黑名单 + 内部术语正则 + 判定词一致。

## 8. 测试方案与记录模板

### 8.1 两层测试，不要混在一起说

| 层 | 测什么 | 输入 | 能证明 | 不能证明 |
|---|---|---|---|---|
| L1 判断层 | 规则准不准、分数稳不稳 | **结构化 JSON**（模拟图像） | 链路正确、可追溯、确定性、排序合理性 | 真实照片能不能认对 |
| L2 感知层 | 认不认得出单品 | **真实照片** | 单品数/主色/正式度的识别准确率 | — |

**只做 L1 会在 L2 翻车，只做 L2 无法定位问题。** 面试交付里两层都要有一个小样例。

### 8.2 用例矩阵（最小可交付版：12 套）

| 维度 | 取值 |
|---|---|
| 场合 | 通勤 / 正式 / 约会 / 休闲 / 运动（5） |
| 用户 | 3 个人设（通勤知性 / 法式约会 / Y2K 街头）× 各带 `banned_styles` |
| 难度 | 明显好 4 / 明显差 4 / 边界 4（边界=单维度刚好卡阈值） |
| 真实照片特例 | 遮挡、下半身裁切、多人、平铺（各 1 张，专门测诊断而非分数） |

### 8.3 记录模板（CSV，一条一套）

| 列 | 说明 |
|---|---|
| `case_id` | 唯一 ID，如 `c07_y2k_casual` |
| `image` | 图片路径或 `json:case07.json`（标明是模拟还是真图） |
| `profile_id` / `occasion` | 用户与场合 |
| `system_verdict` / `system_total` | 系统结论与分数 |
| `human_verdict` / `human_total` | 人工（盲评，先写不看系统） |
| `diff` | 分数差（系统 − 人工） |
| `attribution` | **感知错 / 语义错 / 规则错 / 文案错 / 接受**（五选一，必填） |
| `top_hits` | 前 3 条命中的 `rule_id`（方便查是否同一规则反复误伤） |
| `notes` | 一句话，写明"哪一层出的问题" |

### 8.4 验收门槛（附本仓库实测值，可直接引用）

| 指标 | 门槛 | 实测 | 结论 |
|---|---|---|---|
| 总分 Spearman ρ（vs 人工分） | ≥0.60 | **0.8408**（p=3e-06） | ✅ |
| Verdict 四分类准确率 | ≥65% | **75.0%**（15/20） | ✅ |
| 扣分可追溯率 | 100% | **100%**（49 项） | ✅ |
| 确定性（同输入两次跑） | 100% | **100%**（20×2） | ✅ |
| 严重错判（不适合→强烈推荐） | ≤5% | **0.0%** | ✅ |
| 画像区分度（不同用户分差中位数） | ≥8 分 | **8.0**（带偏好）/ 5.0（无偏好） | ⚠️ 必须引导用户填偏好 |

> 引用这些数字时**必须同时说明边界**：这 20 套是**合成**用例，人工分按剧本设计意图给，
> 验证的是"链路与排序"，不是"审美与真人一致"。真实标定需真人照片 + 3 名盲评。

### 8.5 差异归因（这张表比分数更重要）

| 归因 | 判据 | 典型表现 |
|---|---|---|
| **感知错** | 图里明明有，系统没认出来 / 认错了 | 漏了豹纹小包、把包认成裤子 |
| **语义错** | 系统认对了，但落到词表/规则时被曲解或丢弃 | Y2K 被判"与画像无交集" |
| **规则错** | 语义对，规则阈值或豁免写错 | 黑白高对比被罚"明度断层" |
| **文案错** | 结论对，说法错 | `verdict=suitable` 但总评写「一般」 |

**先分感知错还是语义错，再谈优化**——这两类的修法完全相反（一个要模型，一个要词表）。

## 10. 局限与后续优化

| 局限 | 具体表现（实测） | 短期可做（成本 ≤ 半天） | 不建议现在做 |
|---|---|---|---|
| **图片识别不稳定** | 单次解析有 ±1 件方差；遮挡时把包当裤子（主色偏差 147）；下半身裁切仍硬给结论 | 三次采样投票；缺件就降 `assessability` 并在报告里明说"这条证据不足" | 自训检测模型 |
| **规则与 LLM 冲突** | LLM 说"很搭"，规则扣 −5；用户只信一边 | **规则定结论、LLM 只解释**；冲突时把分歧写进诊断，不静默取一边 | 让 LLM 覆盖规则分数 |
| **用户画像有偏差** | 参考 >5 张会稀释（top1 权重 0.60→0.15）；纯统计画像区分度只有 5.0 分 | 引导传 3–5 张**同风格主线**；强制勾选"绝对不穿"→ 区分度 8.0 分 | 分场景多画像（可后续） |
| **结构化输出不稳定** | 偶发 Markdown 包裹、字段缺失、枚举外词汇 | `json_object` + 重试 1 次 + 枚举白名单 + 字段默认值 + 记诊断 | 上 function calling 全家桶 |
| **上限不可达 / 分数虚高** | 曾最高只能到 79 分，"强烈推荐"恒不可达 | 先查误伤与死规则，**不要动基准分** | 调阈值凑分布 |
| **评测集是合成的** | Spearman 0.84 只证明链路正确 | 采 20 套真人照片 + 3 名盲评 | 用合成集对外宣称"审美准确率" |

**后续优化方向（按性价比）**：
① 画像页强制"3 个绝对不穿 + 2 个想尝试"（半天，区分度 5.0→8.0）；
② 风格家族别名表持续扩充（每加一个真实说法就多救回一段信号）；
③ 单品 bbox 交叉校验（两个单品落在同一区域 → 冲突降级），治遮挡；
④ 三次采样投票降方差（成本 ×3，只在高价值场景开）。

## 11. 问题解决：出的问题与怎么解的

> 这一节是整份文档里最值钱的部分。**结论先说**：线上"识别不准"的抱怨里，
> 大部分不是模型看错了，而是**语义在词表 / 规则 / 文案 / UI 之间被曲解或丢弃**。

### 11.1 主案例：模型其实看对了，是我们的词表把它扔了（语义失真）

**现象**：用户 5 张 Y2K 街头参考 + 1 套「薄荷绿波点连帽衫 + 黑波点短裤 + 棕托特 + 黑乐福白袜 + 豹纹小包」。
用户判断"也是 Y2K 古早混搭"，系统给 **56 分「一般」**，还建议"换掉西装外套"（这套根本没有西装）。

**四层根因（逐层叠加，全部静默）**

| 层 | 问题 | 后果 |
|---|---|---|
| 词表 | 25 个受控词里**没有 Y2K / 千禧 / 古早 / 原宿 / 辣妹**，模型自由输出的"日系少女/居家/学院风"全部映射为 0 | 个性化信号整段丢失 |
| 比对 | 规则用**字符串精确比对**：`Y2K` vs `日系少女` → 判"毫无交集" | D2 从 18 打到 5（−5 扣分） |
| 正式度 | prompt 只写"formality 1–5 的整数"，**没定义方向**；模型把卫衣/卫裤/运动鞋全标 5 | 归一化后变成"最正式"，`preferred_formality=4`，假扣"正式度跨度冲突" −4 |
| 色相 | `hue_span` 把**黑白灰**也算进色相（黑=0°，白=0°） | "薄荷绿 + 黑"算出 168° 撞色，假扣 −2 |

**修法（不动向量维度，加一层"风格本体"）**

1. 建 13 个**风格家族**，每族 = 显示名 + 受控代表 + 别名表；`Y2K/千禧/古早/原宿/辣妹` → 「千禧辣妹」。
2. 解析阶段就展开：`Y2K` → `甜酷 + 街头潮流`（向量真正吃到信号）。
3. 规则改成"**词面无交集 且 家族也无交集**才扣分"；同源度取 `max(词面, 家族)`。
4. `formality` 改用描述词（`casual` → 2），并按品类关键词做确定性夹逼（卫衣→≤2，西装→≥4）。
5. `hue_span` 只统计 `saturation ≥ 0.15` 的有彩色。
6. 主色计数先聚类（三双黑鞋算一个主色）。
7. 建议模板禁止假设具体单品，禁止"那件/它"这类指代。

**实测（同一组图片，改前 → 改后）**

| 指标 | 改前 | 改后 |
|---|---|---|
| 判定 | 一般（neutral） | **适合（suitable）** |
| 总分 | 56.0 | **74.0** |
| D2 风格一致性 | 5.0 / 25 | **21.0 / 25** |
| 识别到的风格 | 日系少女/居家/学院风/JK制服 | **甜酷/街头潮流/复古** |
| 假扣分 | 4 条（−15） | **1 条（−2，真撞色）** |
| 离线评测 verdict 准确率 | 65.0% | **75.0%** |

**这次最贵的教训**：**"识别不准"要先分清是感知错还是语义错**。
感知错要去换模型；语义错只要改词表与比对方式，**成本差 100 倍**。

### 11.2 其他 9 个问题（都付过代价）

| # | 现象 | 根因 | 修法 | 实测 |
|---|---|---|---|---|
| 1 | 分数最高只能到 79，"强烈推荐"永远不可达 | 有规则在**错误扣分**（黑白高对比被罚）+ 有 boost 规则阈值不可达（死规则） | 加豁免 + 按后端重标定阈值；**不动基准分** | 分数区间 45.4–79.0 → 36.4–81.0；强烈推荐 0% → 4.0% |
| 2 | 34% 的规则在真实解析能力下毫无区分度 | 依赖的字段（腰线/塞衣角/重心）解析层根本喂不出来 → 恒命中/恒不命中，**静默失效** | 给规则加"正负夹具"；先用 `assessability` 门控，拿不到证据的维度不下判断 | 50 条里 17 条字段恒定，已识别并分期补 |
| 3 | 换了 embedding 后端，余弦阈值全线失灵 | 阈值是照另一个后端的分布写的 | 按后端设两个锚点做单调归一化后再喂规则 | 视觉后端 0.79 → 0.55（同刻度）；哈希后端保持恒等 |
| 4 | 页面显示完整画像，但**不是看用户的照片** | 8 个参考标识都不可解析 → 静默降级 mock，生成 8 套虚构搭配 | 报告自我声明 `data_source`；降级时页面顶部红条；告警去重计数 | mock 假数据给了 78 分「适合」，真图 47.2「不适合」——**假数据往往更漂亮** |
| 5 | 用户粘贴真实路径，5 张照片全被判"不是图片" | Windows「复制文件地址」带引号，`Path('"E:\a\1.jpg"')` 恒不存在 | 统一 `normalize_ref`：去引号（最多 3 层）/去 `file://`/去空白 | 5/5 拿到视觉向量，无降级 |
| 6 | `verdict=suitable`，总评却写「一般」 | `(str, Enum)` 的 `str()` 返回 `'Verdict.suitable'`，查表落空走默认值 | 统一 `verdict_key()` 收口，只用 `.value`；再用正则兜底替换 | 判定词与总评一致 |
| 7 | 8 张参考产生 30 条"告警"，用户以为全坏了 | 成功信号与失败同色同字号；丢失"第几张"的归属；没有"影响什么" | 诊断分级 `info/warn/error` + 归属 `refs` + 影响说明；成功信息折叠 | 30 条一行流 → 「证据质量 8/8 · 5 条需处理 · 遮挡在第 2 张」 |
| 8 | 参考越多越"不准" | 等权平均 → 参考集越杂越像"平均人"（top1 权重 0.601→0.151） | 建议 3–5 张同风格主线；超 5 张给诊断提示（限上限属于契约，给建议属于产品） | 3 张同风格区分力 20.8 分 > 6 张混杂 15.8 分 |
| 9 | 冷启动用户，三个不同人设给出同样的分数 | 75% 的维度与用户无关，个性化被锁在单一维度 25% 权重里 | 让用户声明"绝对不穿/想尝试"，复活禁用风格硬规则 + 探索加分 | 区分度 5.0 → **8.0 分**（门槛 8），verdict 分歧率 32% → 50% |

### 11.3 排障顺序（可复用）

1. **看 `data_source`**：是不是 mock？是就停下，别拿假数据下结论。
2. **看诊断**：是"看不见"（感知错）还是"看见了没认出来"（语义错）。
3. **看 `rule_hits` 的 `evidence`**：规则读到的值，和你在图里看到的值，是不是同一个东西。
4. **看 `ledger`**：分数是被哪条规则吃掉的？有没有被预算截断（`clipped`）？
5. **看文案**：结论对不对、说法对不对——两者可能一个对一个错。
